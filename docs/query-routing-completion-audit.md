# Query-Routing Redesign — Completion Audit

**Date:** 2026-07-28
**Scope:** Phase 0 of the post-Milestone-2 continuation plan. Read-only — no implementation code changed to produce this document.
**Method:** Every finding below was verified against the actual repository this session (file reads, greps, `wc -l`, targeted test-file inspection) — not recalled from memory. Where a finding rests on session memory rather than a fresh read in this pass, it's marked explicitly.

---

## 1. Executive summary

The classifier/registry/routing architecture is solid and matches the spec's intent closely: 28 types, active/disabled/handoff separation, a single routing authority, zero-model-run guarantees for non-active outcomes, and a 200-row acceptance matrix built directly from this spec (verified verbatim in spot checks). 19 of 28 types are active with a full dedicated stack; 2 are protected handoffs to already-live, separately-built features; 7 are honestly disabled.

Two things are **not** true, though, and both are load-bearing for Phases 1–2 of the new plan:

- **Adaptive schema output is never persisted to Firestore.** `completeRun()` (`lib/firestore/runs.ts`) writes only the legacy per-model raw text and legacy V1 synthesis cache. No `queryType`, `answerShape`, `CommonResponseMeta`, or any of the 9 Milestone-2 result shapes (`rankedEnumeration`, `decisionSupport`, etc.) ever reaches Firestore. A Milestone-2 run only exists in the browser tab that produced it — reload the page or revisit it from history and the adaptive answer shape is gone.
- **Governance is hard-wired to a three-way `runType: "research" | "verification" | "video"` model**, unaware of the 28-type taxonomy. `CommonResponseMeta` is built in exactly one place (`routeClassifiedQuery.ts`, for non-execution responses only) — zero of the 19 active schemas' successful results ever populate it.

Both are consistent with what was already flagged as deliberate, tracked debt in `technical-documentation.md` — this audit doesn't change that call, it just makes the blast radius concrete before Phase 1/2 work begins.

## 12. What Phase 1/2 as scoped actually depend on

Reading the new prompt's Phase 1 and Phase 2 against what's verified above, two adjustments are worth flagging before work starts:

1. **Phase 1 needs a persistence sub-step that isn't explicitly named.** "Thread meta through... persistence" (Phase 1, requirements 5–6) presumes an existing `adaptive` write path to extend additively. There isn't one (§6). Phase 1 should include, as its own reviewable increment: extend `completeRun()`/`createRun()` to optionally accept and persist the adaptive payload (schemaId, classification, and — once built — CommonResponseMeta), then extend `GET /api/user/runs/[runId]` and the panel-history route to return it. This is squarely "additive, optional field" work per the non-negotiable backward-compatibility rule, but it's real scope, not a byproduct of adding `CommonResponseMeta` to the alignment modules.
2. **Phase 2's "audit existing export behavior" has nothing to audit.** Export doesn't exist for runs today (§8). That phase should be re-scoped from "update exports" to "build minimal export," which is a bigger lift than the prompt implies.

Neither of these blocks starting Phase 1 — they just mean Phase 1's real boundary is larger than "wire a type into 9 alignment modules and 4 UI files."

## 13. Verified plan going into Phase 1

Given the above, the recommended sequencing (unchanged in spirit from the new prompt, adjusted for the persistence dependency):

1. **Phase 1a** — `CommonResponseMeta` computed and threaded through `AdaptivePanelResult` → `route.ts` → `ResultsDisplay.tsx` → `AdaptivePanelResponse.tsx` → all 9 renderers (in-memory only, matches the prompt as written).
2. **Phase 1b** (new, surfaced by this audit) — persist `schemaId`/`classification`/`CommonResponseMeta` additively on the run document; extend the two read paths (`user/runs/[runId]`, `panel-history`) to return it; prove old runs still load with `meta` absent/undefined.
3. **Phase 2**, unchanged, but now has real ground to stand on since 1b gives it a persisted record to attach a decision receipt and review status to.
4. **Phase 3** (registry capability metadata) can happen any time after Phase 0 — it has no dependency on 1/2 and is low-risk, purely additive.
5. **Phase 4** (scenario_analysis, step_by_step_plan, transformation) should follow the established one-schema-at-a-time discipline exactly as it did for the 9 Milestone-2 schemas, and per the non-negotiable rules, each one now also needs Phase 1/2 integration (CommonResponseMeta + decision receipt) as part of its own "full stack" bar, not bolted on after.

**This audit recommends Phase 1a and 1b be treated as one reviewable unit** (the prompt's own rule 5 — "do not retrofit major cross-cutting behavior one schema at a time" — applies equally to splitting persistence away from the meta it's meant to persist).

## 30. Addendum — Pure Multi-Reviewer Aggregation Engine and Quorum Truth Tables, Part D, now live (2026-07-31)

Full detail in `docs/governance-decision-receipts-design.md` §32. **This step is pure domain logic only** — no route, no Firestore read/write, no `governanceRecord` write, no panel-status write, no audit/history/events, no UI. `aggregateAdaptiveReviewVotes()` (`lib/governance/adaptiveReviewAggregation.ts`) is a standalone, importable, independently testable pure function that nothing in this codebase calls yet.

**What changed:** the function consumes a panel configuration and its current-revision votes and returns one of `waiting` (quorum not yet met), `deadlocked` (quorum met, no strict group majority), `ready` (a deterministic terminal outcome with a supporting-reviewer set and condition-count-only metadata), or `invalid` (12 distinct, deterministic reasons). Quorum means "minimum submitted votes before a majority is even evaluated," not a winning threshold itself. A group (approval: `approved`/`approved_with_conditions`; blocking: `changes_requested`/`rejected`) wins only with a strict majority of SUBMITTED votes — never of total reviewers, never of the quorum value, never by plurality or tie-break. Within a winning group, any `approved_with_conditions` vote escalates the result (conditions are never silently dropped) and any `rejected` vote escalates the result (rejection is never silently downgraded) — but a MINORITY group's votes never override the winning group (no rejection veto: 2 approved + 1 rejected → approved). Reuses the existing panel/vote parsers (already pure, already established in Parts B/C) as its structural-validity layer rather than reimplementing shape validation a third time, layering only the genuinely aggregation-specific checks (panel openness, cross-vote-to-panel referencing, duplicate-vote detection) on top.

## 34. Addendum — Auth Lifecycle Hardening: Client/Server Session Synchronization, Step 6, now live (2026-08-01)

Full detail in `docs/operations/auth-session-sync-runbook.md`. **Prompted directly by §33's own security review**, which disclosed a cross-cutting session-identity desync reproduced during that step's live browser testing: a `__session` cookie left over from a PREVIOUS user could keep authorizing protected requests as the wrong identity after a different user signed in on the same browser — root cause traced to `getRequestUid()` (`lib/teams/teamApiAuth.ts`, used by every team/governance route) trusting a valid cookie unconditionally whenever one was present, never checking whether an accompanying bearer token disagreed, compounded by `app/login/page.tsx` treating an unverified, fire-and-forget session-cookie POST as sufficient for "signed in" and `components/TopNav.tsx`'s logout never calling `DELETE /api/auth/session` at all.

**What changed:** `getRequestUid()` now rejects a request outright (401) when a valid cookie and a valid bearer token independently decode to DIFFERENT uids — a bearer token that is merely absent, malformed, or expired remains a non-conflict, the cookie alone stays sufficient exactly as before. `components/AuthProvider.tsx` is rebuilt around an explicit session-synchronization state machine (`lib/client/authSessionStateMachine.ts`: `signed_out | authenticating | syncing_session | authenticated | signing_out | session_error`), driven by `onIdTokenChanged` (not `onAuthStateChanged`, since silent token refreshes need the same re-sync) and guarded by an operation-generation counter (`lib/client/authGeneration.ts`) so a stale async result can never overwrite newer state. `lib/client/sessionSync.ts` is the sole client-side caller of the session endpoints, which gained a new `GET` (reports `{authenticated, uid?}` only) alongside a hardened `POST` (server-derived uid only, returns it for client verification) and `DELETE` (cookie-attribute-matched deletion, so a "clear" can't silently fail to actually clear the browser's copy). Login/signup now invalidate any existing different session before signing in, and wait for `syncState === "authenticated"` for their OWN uid — not merely "Firebase resolved a credential" — before redirecting. Logout now awaits the server cookie's actual deletion before presenting a signed-out state. Every multi-reviewer governance mutation button (vote/finalize/override/reconfigure/cancel) additionally gates on the new `canMutate` derived value, not just the presence of a Firebase user object.

**A real bug was found and fixed during this step's OWN manual verification**, not just in the original audited code: the login/signup pages' pending-redirect tracking initially used a React ref rather than state, which meant that if `AuthProvider`'s reactive sync completed BEFORE the page armed its own "wait for this uid" check (a genuine race, since the two run independently), the watching effect would never be re-triggered to notice — the button would hang until a 10-second timeout force-failed it, even though the login had actually succeeded. Fixed by switching to `useState`, which correctly re-evaluates against current context on arming regardless of ordering; caught live in the browser, not by the unit tests (which mocked the dependency directly and so couldn't reproduce the timing race), reinforcing why this step's own "must verify live" requirement mattered.

**Manual verification** used two real seeded, non-production identities in a real browser against this repo's actual (only) Firebase project: login (including a persisted-session restore across a fresh tab), a direct account switch via the login form (old session invalidated first, new one established, server uid confirmed via `GET /api/auth/session`), logout (server session confirmed cleared, a protected endpoint confirmed to return 401 immediately after), and multi-tab behavior — verified TWO distinct ways: (1) a tab left open when logout happens elsewhere reactively transitions to a signed-out state (Firebase's own cross-tab persistence propagates the `onIdTokenChanged(null)` event) with no manual reload; (2) an account switch performed in one tab reactively updates a SECOND, already-open tab's displayed identity, capability flags (Owner Override correctly disappearing for a non-owner), and vote attribution — all without a reload. A governance regression check confirmed role-sensitive UI (the owner-only Override section) correctly tracked the live, server-confirmed identity through every switch.

**Disclosed, NOT fixed in this step (deliberately out of scope):** 14 other route files independently reimplement the same cookie-first pattern `getRequestUid()` had — including the protected Claim Verification, Video Verification, `run-panel`, and `synthesize-panel` routes, explicitly off-limits to modify in this step. The fix here is scoped to the team/governance route family this engagement is actually gating for release; centralizing the pattern into one shared, reusable helper is recommended follow-up work.

Full suite: 2902/2902 passing (up from 2807 — 9 new test files covering the pure state machine, the generation guard, the session-sync client helpers, the hardened session route, the `getRequestUid` cross-check regression, the server/client telemetry wrappers, and source-level wiring guarantees for `AuthProvider`/`TopNav`/login/signup), confirmed stable across two consecutive runs. `tsc --noEmit` and `next lint` both clean.
