# ConvergePanel — Technical Documentation

## Overview

ConvergePanel is a multi-LLM research and verification platform built on Next.js 14 (App Router). It runs five AI models in parallel to produce cross-model analysis, detect disagreement, and create auditable records for high-stakes decisions. The platform has three core operating modes — Deep Research, Claim Verification, and Video Verification — plus an automated Synthesis layer and, on the Full plan, a team Governance system.

**Tech stack:** Next.js 14 App Router · Firebase Auth + Firestore · Stripe billing · Node.js runtime (all API routes use `export const runtime = "nodejs"`)

## Authentication

Two credential paths are accepted by every API route:

1. **Session cookie** `__session` → `verifySessionCookie()` from `lib/firebase/auth-helpers.ts`
2. **Bearer token** `Authorization: Bearer <idToken>` → `verifyIdToken()` from `lib/firebase/auth.ts`

**Middleware** (`middleware.ts`) only checks for cookie *presence* to gate `/admin/*` routes. Full token validation and custom claim checks happen inside each API route.

**Admin access** is a Firebase custom claim `admin: true` — not a database field. The `ADMIN_EMAILS` env var controls which accounts can be granted admin status.

**Admin routes** (`app/api/admin/*`) must use `requireAdminApiAccess()` from `lib/firebase/auth-helpers.ts`, which verifies both token validity and the `admin: true` custom claim. Using `verifySessionCookie()` alone on admin routes is a privilege escalation vulnerability — it only confirms a valid session, not admin status.

### Auth Lifecycle Hardening (Step 6) — client/server session synchronization, now LIVE

**Root cause fixed:** `lib/teams/teamApiAuth.ts`'s `getRequestUid()` (used by every team/governance route) checked the `__session` cookie FIRST and, whenever a valid cookie was present, used its uid **unconditionally** — the request's `Authorization: Bearer` token was never even consulted. Combined with two independent client-side gaps — `app/login/page.tsx` treating a fire-and-forget, unverified session-cookie POST as sufficient for "signed in," and `components/TopNav.tsx`'s logout calling only the Firebase client SDK's `signOut()`, never `DELETE /api/auth/session` — a `__session` cookie left over from a PREVIOUS user on the same browser could silently keep authorizing requests as the wrong identity for up to its full 5-day lifetime, regardless of what the UI displayed. Reproduced concretely and closed by this step. Full writeup, reproduction steps, and the complete fix inventory: `docs/operations/auth-session-sync-runbook.md`.

**`getRequestUid()` now cross-checks**: if a request carries BOTH a cookie and a bearer credential, BOTH must independently validate AND resolve to the SAME uid, or the request is rejected (401) — **updated by Step 7's recovery pass** (see below): the original Step 6 version of this cross-check treated a valid cookie alongside a merely invalid/expired bearer as non-conflicting and authenticated via the cookie alone; live verification later found that carve-out itself unsafe, and it no longer exists.

**`components/AuthProvider.tsx`** now owns an explicit session-synchronization state machine (`lib/client/authSessionStateMachine.ts`): `signed_out | authenticating | syncing_session | authenticated | signing_out | session_error`. `syncState === "authenticated"` is the ONLY state in which the Firebase client uid and the server session-cookie uid are confirmed to match — exposed via `useAuth()` as `syncState` and the convenience boolean `canMutate`. Listens to `onIdTokenChanged` (not `onAuthStateChanged`, since token refreshes need the same synchronization), guarded by an operation-generation counter (`lib/client/authGeneration.ts`) so a stale async result (an old login response, a refresh after logout, a rapid A→B→A switch) can never overwrite a newer state. `lib/client/sessionSync.ts` is the sole client-side caller of `POST`/`DELETE`/`GET /api/auth/session` — login/signup wait for `syncState === "authenticated"` for their OWN uid before redirecting; logout awaits the server cookie's deletion before considering itself complete; every governance mutation button additionally gates on `canMutate`, not just `user`.

**`GET /api/auth/session`** (new) reports `{ authenticated, uid? }` only — used by `lib/client/sessionSync.ts`'s `verifyClientServerIdentityMatch()` for defense-in-depth identity checks on sensitive route entry.

**Known, disclosed, NOT fixed in this step**: 14 other route files (`app/api/verify-claim`, `verify-video`, `run-panel`, `synthesize-panel`, `billing/*`, `user/*`, etc.) independently reimplement the same cookie-first pattern outside `teamApiAuth.ts`. Several are protected Claim/Video Verification paths explicitly out of scope for this step to touch. The pattern is the same one fixed in `getRequestUid()`; centralizing it into one shared helper is recommended follow-up work, not done here. **This was completed in Step 7 below.**

### Repository-Wide Auth Identity Consistency Remediation (Step 7), now LIVE — closes every remaining cookie-first path

`lib/auth/resolveRequestIdentity.ts` is now the ONE shared, hardened credential-resolution contract used by every protected route in the app — generalized from Step 6's `getRequestUid()` fix. A repository-wide search (not just `app/api`) found the true count was **19 routes across 15 code locations**, not 14: the originally-disclosed 14 routes, plus 5 governance routes (`audit`, `audit/backfill`, `review`, `queue`, `policy`) found only via a cross-route search, since they shared the vulnerability indirectly through one helper (`resolveGovernanceRequestUser()`, `lib/governance/authCheck.ts`) that a route-file-only search missed. Combined with Step 6's 15 team/governance routes, **34 routes total** now resolve identity through this one contract. `getRequestUid()` and `resolveGovernanceRequestUser()` are both now thin, behavior-preserving wrappers around it — never forked implementations.

**Claim Verification (`app/api/verify-claim`) and Video Verification (`app/api/verify-video`)** were migrated with auth-only diffs, explicitly authorized for this step — confirmed via `git diff` that parsing, model dispatch, verdict/consensus computation, quota, token accounting, and audit logic are byte-identical to before; only the auth-resolution block changed.

**Recovery — strict dual-credential validation.** The first version of `resolveRequestIdentity()` preserved Step 6's "valid cookie + merely invalid bearer → authenticated via the cookie" carve-out. Live verification against the real running server found this itself unsafe: a stale cookie for user A alongside an EXPIRED bearer token actually issued for a DIFFERENT user B still authenticated as A. Fixed by removing the carve-out — whenever both a cookie and a bearer credential are present, BOTH must now independently validate AND agree, with no remaining fallback case. Full truth table, the live reproduction, and the fix: `docs/operations/auth-session-sync-runbook.md`.

**Intentionally not modified (audited, found not vulnerable to this pattern)**: `verifyAdminToken`/`requireAdminApiAccess` (`lib/firebase/auth-helpers.ts`, used by `app/api/admin/*`) extract the bearer token FIRST, only ever falling back to the cookie when no `Authorization` header is present at all — the opposite precedence, immune to a stale cookie silently overriding a fresh bearer. `lib/firebase/adminAuth.ts`'s `getRequestUser()` is bearer-only.

No cookie-first or invalid-credential-fallback path remains anywhere in the repository as of this step's completion.

## Rate Limiting

Per-user rate limiting is implemented in `lib/security/rateLimit.ts` using Firestore atomic transactions — no Redis required.

### How it works

- Counters are stored in the `rate_limits` Firestore collection, keyed by identifier (e.g., `run-panel:${uid}`)
- Each check runs inside a Firestore transaction (`runTransaction`) to prevent race conditions under concurrent requests
- If a window has expired, the counter resets automatically within the same transaction
- On Firestore unavailability or any error, the function **denies** the request (fail-closed)
- Stale documents are cleaned up opportunistically on ~1% of requests via `cleanupRateLimits()`

### Interface

```ts
checkRateLimit(config: {
  maxRequests: number   // requests allowed in window
  windowSeconds: number // window size
  identifier: string   // unique key, e.g. "run-panel:uid123"
}): Promise<RateLimitResult>

// RateLimitResult
{
  allowed: boolean
  remaining: number
  resetAt: Date
  retryAfter?: number  // seconds; only present when !allowed
}
```

All logging uses `logger` from `@/lib/logger` — never `console.error`.

## Deep Research — Panel Mode

### Request flow

`POST /api/run-panel` → `lib/panel.ts` → `runPanel()`

The panel queries all selected models concurrently using `Promise.allSettled`. Each connector must never throw; it always returns a `ModelResult` with `status: "ok" | "error" | "timeout" | "refused" | "rate_limited" | "substituted"`.

### Retry and fallback logic

1. First attempt — all selected models queried in parallel
2. Transient errors (`timeout`, `rate_limited`, `refused`) trigger up to **2 retries** with exponential backoff
3. After retries, failures for OpenAI / Anthropic / Google providers fall back to **DeepSeek** (controlled by `PANEL_DEEPSEEK_FALLBACK_FOR` env var; defaults to `openai,anthropic,google`)
4. If fallback also fails, the slot becomes a failed placeholder
5. Public status is normalized to `"ok" | "substituted" | "failed"` — callers never see internal retry states

### Deep Research prompt structure

Built by `buildPanelPrompt()` in `lib/panelPrompt.ts`. The prompt instructs each model to follow a 6-stage internal workflow and produce output in 10 named sections:

1. Summary
2. Key Claims
3. Evidence and Reasoning
4. Uncertainties and Disagreements
5. Potential Biases and Blind Spots
6. Key Metrics
7. Methodology and Assumptions
8. Alternative Perspectives
9. Gaps in Evidence / Open Questions
10. Practical Implications and Suggested Follow-Up Questions

Target output length: 900–1,400 words per model.

### Adaptive Result Schema System (flag-gated, LIVE IN PRODUCTION as of 2026-08-05)

Alternative to the fixed 10-section template above. Behind `ADAPTIVE_SCHEMAS_ENABLED` (`lib/env.ts`, defaults `false` when unset). When on, `/api/run-panel` classifies the query once before fan-out and has every model answer a typed JSON schema instead of the markdown template — comparable atomic units (claims, metrics, steps, scenarios) instead of free-text sections.

A second flag, `ADAPTIVE_VERIFICATION_ENABLED` (also `lib/env.ts`, defaults `false` when unset, independent of the first), turns on the full verification layer on top of the aligned matrix: agreement/certainty scoring, the pass/caution/fail gate, the Synthesis Report, and the Trust Summary. With `ADAPTIVE_SCHEMAS_ENABLED=true` alone, adaptive runs render only the bare per-schema comparison view (`AdaptiveResultsView`) with an unscored claims matrix — no tabs, no gate, no synthesis. Both flags need to be on for the restored three-tab experience described below.

**Production status:** neither flag was ever set in the production Vercel environment prior to 2026-08-05 — confirmed via `vercel env ls production` while verifying the classifier fix below (every production run showed `adaptiveOutput`/`adaptive.status: "absent"`, i.e. the entire system below, despite being fully built and tested, had never actually run against a real production request). Both flags were added to production and the current deployment redeployed on 2026-08-05, and the Comparison/Risk-Analysis renderer fix (next subsection) was confirmed live immediately after. No prior incident — this system's activation was simply never completed as a deploy step.

All modules live in `lib/adaptiveSchema/` and the renderers in `components/adaptive/`:

| Step | Module | What it does |
|------|--------|---------------|
| 1. Classify | `classifier.ts` | One Gemini call (`callGemini` + `systemPromptOverride`), 8s timeout (raised from an original 3s — see the "Known gaps" note below), LRU-cached. Falls back to `"generic"` on timeout/error/malformed JSON/confidence < 0.6. Never blocks the run. |
| 2. Select schema | `schemaRegistry.ts` | 28 `QueryType`s as of the query-routing redesign (Milestone 1) — see the dedicated subsection below — each with a fixed field list (no optional "(if applicable)" sections) and an `implementationStatus`. |
| 3. Build prompt | `promptBuilder.ts` | Renders only the schema's fields into the model's system prompt, with per-field word/item caps and inline interface docs for `Claim`/`Metric`/`Step`/`Scenario`. |
| 4. Validate | `validator.ts` + `enumCoercion.ts` | Before Zod sees it, recoverable enum drift on any claim-shaped field is coerced (case/synonym-normalized — e.g. Gemini's `"agrees"` → `"asserts"`; confidence/evidenceType only get formatting normalization, never semantic reinterpretation), then Zod-validated. A whole-object parse failure falls back to field-level salvage: array fields (`claim[]`/`metric[]`/`step[]`/`scenario[]`/`string[]`) keep whichever items validate and drop only the broken ones; scalar fields are all-or-nothing. Only fields with zero recoverable content end up in `invalidFields`; the model result stays `ok: true` as long as anything survived. Soft-truncates over-cap fields (logged). If required fields are still invalid after salvage, `orchestrate.ts` re-prompts that model exactly once with the validation errors appended (`retried: true` on the merged result) — a second failure keeps whatever salvage already recovered. Only when literally nothing survives (malformed JSON, non-object response, or salvage+retry both come up empty) does the result become `parseError`/`ok: false` (rendered as a failed cell, never crashes). |
| 5. Align claims | `alignment.ts` + `fieldAlignment.ts` | `claim[]` fields: exact/fuzzy slug match first, then a cheap-model clustering call for whatever didn't cross-match (clusters by *proposition*, so opposing stances on the same question merge into one row), then a batched per-model stance-extraction backfill pass so a null cell means true silence, not a missed match. `metric[]`/`step[]`/`scenario[]`/scalar fields go through dedicated structural unitizers. All produce `AlignedClaim[]` — one universal matrix regardless of source field type. |
| 6. Score agreement | `agreementComparators.ts` | Schema-specific agreement semantics: numeric tolerance bands (financial), jurisdiction hard-key mismatch (legal), scenario probability bands (forecast), evidence-tier weighting (medical), order-sensitive step matching (procedural), stance-based (contested/generic). |
| 7. Score certainty | `scoring.ts` | Per-claim: `0.35*coverage + 0.45*agreement + 0.20*statedConfidence`. Per-run: salience-weighted mean, with a 3x evidence-tier multiplier for medical_health. Weights in `config.ts`. |
| 8. Gate | `gate.ts` | pass/caution/fail from run certainty + load-bearing (top-3 by salience) claim splits. Thresholds in `config.ts`. |
| 9. Synthesize | `synthesisReport.ts` | One model call producing Unified Answer (only from consensus/majority claims, with model attribution), Panel Verdict, agree/disagree lists, and schema-aware narrative sections. Degrades to "Panel could not converge" on a `fail` gate. |
| 10. Trust summary | `trustSummary.ts` | Per model: claims contributed, majority alignment, citation presence (`Metric.source`/`factual_lookup.source`, neutral 1.0 for schemas with no sourceable field), contradiction count, parse health, and a composite `trustScore` weighted per schema (`TRUST_WEIGHTS_BY_SCHEMA` in `config.ts`). |
| 11. Orchestrate | `orchestrate.ts` | Glue called from `app/api/run-panel/route.ts`: `planAdaptiveRun()` before `runPanel()`, `finalizeAdaptiveRun()` after — steps 6–10 only run when `ADAPTIVE_VERIFICATION_ENABLED` is on. |

`runPanel()` (`lib/panel.ts`) takes an additional optional 5th argument, `perModelPromptOverrides`, threaded through to each model's **primary** call only — the DeepSeek fallback path doesn't support prompt overrides, so a substituted slot in adaptive mode falls back to the legacy template and gets validated as a `parseError` (a failed cell, not a crash).

The API response includes an `adaptive` object (`classification`, `schemaId`, `results`, `alignedClaims?`, and — when `ADAPTIVE_VERIFICATION_ENABLED` — `gate`, `synthesisReport`, `trustSummary`) alongside the normal `results` array. On the client, `ResultsDisplay.tsx` renders `AdaptivePanelResponse` — a three-tab shell (List View / Compare View / Synthesis Report, mirroring the legacy layout) that falls back to the bare `AdaptiveResultsView` when `gate`/`synthesisReport` are absent. This entirely replaces Trust Summary / Agreement Map / legacy List-Compare-Synthesis and skips the client-side `synthesizeReport()` call and the `/api/synthesize-panel` auto-trigger — that whole markdown-parsing consensus engine (`lib/agreementMap.ts`, `lib/consensus.ts`, `lib/synthesis/*`) is untouched and still used for the flag-off path.

**Known gaps:**
- History replay is persisted for the 9 Milestone-2 schemas only (`PersistedAdaptiveOutputV1`, Query-Routing Redesign Phase 1 persistence, below — reload via `GET /api/user/runs/[runId]` + `adaptPersistedOutputToPanelPayload()`). The 8 original/legacy-shell schemas plus `factual_lookup` are still not persisted — reloading one of those shows `TopSummaryBar`'s Status as `Incomplete` (no governance record either, for the same reason), not a crash, but the schema-specific view itself is unavailable on reload.
- The classifier/cluster/backfill helper calls (all Gemini-based) can time out under real concurrent load (observed live: classifier falling back to `"generic"`, cluster/backfill leaving pass-1 groups as-is) — each degrades gracefully (never blocks the run) but reduces classification/clustering quality rather than failing loudly. Worth tuning timeouts or moving to a dedicated fast model if this shows up often in production.

A dev-only debug panel (`AdaptiveDebugPanel` in `components/ResultsDisplay.tsx`, gated on `NODE_ENV !== "production"`) shows the classification, schema id, gate status, per-model validation status (ok/salvaged/parseError, invalid fields, retried flag), a full enum-coercion log (model/path/field/raw/coerced), and per-claim score breakdown (coverage/agreement/statedConfidence) for tuning weights. The production-facing `FailedResultsNote` (`components/adaptive/shared.tsx`) shows a plain-English message ("X returned an incompatible format and was excluded from comparison") with the raw `parseError` behind an expandable `<details>`, only for models where nothing survived salvage.

Tests: `lib/adaptiveSchema/__tests__/*.spec.ts` — classifier fallback, prompt snapshots per schema (including the per-field enum/example hint on `claim[]` fields), validator caps/truncation/enum-coercion/field-salvage (including a Gemini stance-drift regression fixture), a dedicated `enumCoercion.spec.ts`, alignment (including an R3 regression fixture merging opposing-stance claims about the same proposition under unrelated slugs), field alignment, agreement comparators per schema, certainty/gate/trust-summary formulas, synthesis report snapshots per schema, an orchestration retry test (`orchestrateRetry.spec.ts` — one-shot re-prompt on validation failure, never loops), and two integration tests (flag-off unscored-matrix path, flag-on full pipeline producing a dense matrix + gate + synthesis report + trust summary for all 5 models).

#### Query-routing redesign (Milestone 1)

Widens the classifier/registry above from 9 `QueryType`s to 28, and adds a routing layer so an unfinished or out-of-scope schema can never reach a live renderer. **Deep Research only** — Claim Verification and Video Verification remain entirely separate, dedicated features (own routes, own pipelines, own UI); this redesign does not unify them. Milestone 1 is architecture-only: no existing schema's prompt, fields, parser, or verification behavior changed, except one deliberate rendering change to `factual_lookup` (below).

**Classification metadata** (`lib/adaptiveSchema/types.ts`) — every classification now also carries: `riskLevel` (casual/professional/high_stakes/safety_critical), `evidenceRequirement` (low/medium/high/regulated), `freshness` (timeless/date_sensitive/recent/live), `inputType`, `verificationMethod`, `requestedCount` (parsed from phrasing like "top 20"), `requiresClarification`/`clarificationQuestion`, `rationale`, and `handoffTarget` (set only for the two handoff intents below). These are cross-cutting — populated for every schema, including the 9 pre-existing ones, without changing their behavior.

**`SchemaImplementationStatus`** (`"active" | "disabled" | "handoff"`) — every `schemaRegistry.ts` entry declares one. `routeClassifiedQuery.ts` is the single place this is read to make a routing decision:
- `active` → the schema executes normally.
- `disabled` → routes to `graceful_limitation` with a `capabilityReason` specific to that schema (e.g. `document_qa`'s reason names the missing page/section-reference tracking; see the infrastructure audit that produced these reasons, summarized inline in `schemaRegistry.ts`'s comments).
- `handoff` → routes to `graceful_limitation` with copy naming the dedicated feature to use instead (Claim Verification or Video Verification).
- Unrecognized `queryType` or a malformed registry entry → also fails safe to `graceful_limitation`, never throws.

This guarantees no disabled or handoff schema ever reaches `GenericSectionsView`, `AdaptiveSynthesisReportView`, or any other schema-specific renderer — only `LimitationNotice` (`components/adaptive/LimitationNotice.tsx`). Enforced both client-side (`AdaptivePanelResponse.tsx` calls `routeClassifiedQuery` before choosing a renderer) and by an exhaustive test (`schemaRegistryStatus.spec.ts`) that loops every non-active registry entry and asserts it resolves to `graceful_limitation`.

**Milestone 1 registry allocation** (28 `QueryType`s, as originally shipped):
- **Active (10):** the 9 pre-existing schemas, unchanged, plus new `graceful_limitation`.
- **Handoff (2):** `claim_verification` (→ Claim Verification tab), `media_authenticity_review` (→ Video Verification tab) — both are empty registry stubs (no fields, no prompt, no renderer) that exist purely so the classifier has a precise label to detect before the router redirects. The classifier prompt (`classifierPrompt.ts`) explicitly teaches these two as HANDOFF outcomes, not schemas to attempt.
- **Disabled — missing capability (4):** `document_qa`, `document_comparison`, `data_analysis`, `current_live_information` — each gated on a real infrastructure gap confirmed by an audit (page/section-reference tracking, dataset/sandbox/chart infra, and verified live-data retrieval, respectively, are all absent from the codebase today).
- **Disabled — not yet implemented (12):** `definition_explanation`, `causal_explanation`, `ranked_enumeration`, `checklist_taxonomy`, `comparison_matrix`, `deep_research`, `evidence_review`, `bias_blindspot_audit`, `decision_support`, `scenario_analysis`, `step_by_step_plan`, `transformation` — registered for future milestones; `bias_blindspot_audit`'s underlying machinery (three-tier bias/blind-spot detection: `biasDetection.ts`/`coverageAudit.ts`/`diagnostics.ts`) already exists inside every synthesis report, but exposing it as a directly-classifiable standalone schema is separate follow-up work.

**Current registry allocation, after Milestone 2's first nine activations (19 active / 2 handoff / 7 disabled):** `ranked_enumeration`, `comparison_matrix`, `definition_explanation`, `causal_explanation`, `checklist_taxonomy`, `deep_research`, `evidence_review`, `bias_blindspot_audit`, and `decision_support` moved from disabled to active, in that order — see the dedicated subsections below. The remaining 3 not-yet-implemented types are unchanged and will move one at a time, each only after its full stack (prompt, parser, schema validation, alignment, verification logic, renderer, persistence compatibility, analytics, acceptance tests) exists — a component or prompt existing in isolation is never sufficient to flip `implementationStatus` to `"active"`.

**Architectural debt tracked, not retrofitted mid-sequence**: the "recommended payload" shape for each of these nine schemas nominally includes a shared `meta: CommonResponseMeta` envelope (declared in `types.ts` since Milestone 1). None of the nine wire it in — each carries its own bespoke honesty/structure fields instead (`hasLiveQueryLogData`, `hasVerifiedSourceData`, `isAmbiguous`/`sourceBacked`, `sourceBacked`/no certainty score, `checklist_taxonomy`'s plain `notes`, `deep_research`'s `sourceCoverage`/`panelBlindSpots`, `evidence_review`'s derived `overallStrength`, `bias_blindspot_audit`'s three-tier structure, and `decision_support`'s `humanReviewNeeded`/`recommendation.isContested`). This is deliberate: retrofitting `CommonResponseMeta` into schemas one at a time as each activates would leave the architecture inconsistent at every intermediate point. Wiring it in for all currently-active parallel-path schemas at once is real follow-up work, tracked here, not bundled into any single schema's activation.

#### `ranked_enumeration` activation (Milestone 2)

The first schema activated after Milestone 1.5's routing guard, chosen because its answer unit is fundamentally different from every other active schema: a **list item** ranked by position, not a claim weighed for stance. Consensus for this schema means coverage and rank agreement across models, not claim-agreement — so it deliberately does not reuse the `AlignedClaim`/agreement-scoring vocabulary from the claim-matrix pipeline.

**Types** (`lib/adaptiveSchema/types.ts`): `EnumItem` (per-model raw output: `id`, `label`, optional `category`/`rationale`/`sources`, `rank`) → aggregated into `AggregatedEnumItem` (`panelRank`, `coverageCount`/`totalModels`/`coverageRatio`, `sourceRanks` per model, optional `rankVariance`) → assembled into `RankedEnumerationResult` (`items`, `lowConfidenceItems`, `requestedCount`/`actualCount`, optional `shortfallNote`, `rankCorrelation`, and `hasLiveQueryLogData: false` — always false, since no such capability exists; this is a deliberate honesty field, not a placeholder for a future integration).

**Alignment/aggregation** (`lib/adaptiveSchema/enumAlignment.ts`, new — a parallel path, not an extension of `alignment.ts`/`fieldAlignment.ts`): `buildRankedEnumerationResult(perModel, requestedCount)` clusters near-duplicate items across models with the same union-find machinery already used for claim deduplication (`UnionFind`, `slugsMatch`, `textsAreNearDuplicates` from `textSimilarity.ts` — reused, not forked), merging on slug/label similarity with no model call. For each merged item: `panelRank` is the mean of each contributing model's own rank; `rankVariance` is the population variance across `sourceRanks`, computed only when coverage is ≥2 models (a single-rank item has no variance to report, so the field is left `undefined` rather than `0`). Cross-model rank agreement is summarized as a Spearman rank correlation (`1 - (6·Σd²)/(n(n²−1))`), averaged pairwise across every pair of models that share ≥2 items, and is `null` when fewer than two models produced comparable rankings.

Items covered by only 1-2 models are split into `lowConfidenceItems`, shown separately from the main list — but **only when the panel has more than 2 models**. This refinement exists because a 2-model panel's full coverage (2 of 2) would otherwise be misclassified as "low confidence" by a naive `coverageCount <= 2` check; the threshold only fires when `totalModels > 2`, so it actually signals thin coverage rather than a small panel.

Shortfall handling is deliberately honest: if the panel returns fewer distinct items than `requestedCount` (e.g. "top 20" but the panel only agrees on 7 distinct items), `shortfallNote` states the actual count plainly. Items are **never padded** to reach the requested count.

**Prompt/validation**: `promptBuilder.ts` gained an `ENUM_ITEM_INTERFACE` block plus a requested-count instruction (echo `requestedCount` back if the user asked for a specific number, otherwise return as many well-supported items as the model can justify). `validator.ts` gained `EnumItemZod` with field-level salvage and rationale truncation, consistent with every other field type's soft-validation behavior.

**Orchestration** (`lib/adaptiveSchema/orchestrate.ts`): `finalizeAdaptiveRun()` takes an early, fully separate branch for `schema.id === "ranked_enumeration"` that calls `buildRankedEnumerationResult` and returns immediately — `alignedClaims`, `gate`, `synthesisReport`, and `trustSummary` are all left `undefined` for this schema, since none of that machinery applies to a ranked list. `finalizeAdaptiveRun()`'s signature gained an optional 5th parameter, `classification?: QueryClassification`, so `requestedCount` extracted at classification time can reach the shortfall check without re-deriving it.

**Renderer** (`components/adaptive/RankedListView.tsx`, new, wired into `AdaptivePanelResponse.tsx`'s `ranked_list` branch): always shows a fixed honesty banner stating no model has live query-log data backing the ranking; renders the main list with rank badge, label, category, a coverage `TintBadge` ("N of M models"), rationale, and per-model chips; renders `lowConfidenceItems` inside a collapsed `<details>` section, kept visually separate from the main list; shows the shortfall note plainly (no padding) when present; shows a rank-agreement stat line when a rank correlation was computed. Falls back safely to the legacy `AdaptiveResultsView` if `rankedEnumeration` is unexpectedly missing.

**Analytics**: `trackRankedListShortfall(...)` fires from the API route when `rankedEnumeration.shortfallNote` is present — metadata only (counts), never the raw question text, consistent with every other adaptive-schema analytics event.

**Classifier**: `ranked_enumeration` moved from the "not yet supported" section of `classifierPrompt.ts` to the active section, with real decision criteria (ordered/ranked list of items is the atomic answer unit; distinct from `checklist_taxonomy`, which has no meaningful rank order, and from `comparison_matrix`, a small fixed named set compared side by side rather than an open-ended ranking) and `requestedCount` extraction guidance ("top 20", "list 50", "give me 10").

Tests: `enumAlignment.spec.ts` (16 — clustering, coverage/rank/variance math, the low-confidence bucket and its >2-model refinement, shortfall detection, rank correlation), `RankedListView.spec.tsx` (7 — structural renderer tests via `renderToStaticMarkup`, no jsdom), `rankedEnumerationOrchestration.spec.ts` (4 — end-to-end `finalizeAdaptiveRun` proving the parallel path never populates claim-matrix fields, and that classification-provided `requestedCount` reaches the shortfall check).

#### `comparison_matrix` activation (Milestone 2)

The second schema activated, chosen next in the approved sequence because its answer unit is two-dimensional: a **(subject, attribute) cell**, not a single list item or a claim. Unlike every other active schema, neither axis is a fixed field the framework supplies — the model extracts both the named things being compared and the dimensions worth comparing them on directly from the question itself, then fills in the grid.

**Types** (`lib/adaptiveSchema/types.ts`): `ComparisonCell` (per-model raw output: `subject`, `attribute`, `value`, optional `verdict`/`rationale`/`sources`) → aggregated independently along two axes into `AggregatedComparisonSubject` and `AggregatedComparisonAttribute` (`coverageCount`/`totalModels`/`coverageRatio` each) → assembled into `AggregatedComparisonCell` (`valuesByModel`, `coverageCount`/`coverageRatio`, `agreement`, optional `consensusValue`/`verdictTally`) → `ComparisonMatrixResult` (`subjects`, `lowConfidenceSubjects`, `attributes`, `lowConfidenceAttributes`, `cells`, and `hasVerifiedSourceData: false` — always false, the same deliberate honesty pattern as `RankedEnumerationResult.hasLiveQueryLogData`). `AggregatedComparisonCell.agreement` deliberately reuses `AlignedClaimStatus`'s `"consensus" | "majority" | "split" | "single_source"` vocabulary — unlike `ranked_enumeration`'s rank correlation, "do models agree on this data point" means exactly the same thing here that it means for a claim row, so a separate vocabulary would only obscure that.

**Alignment/aggregation** (`lib/adaptiveSchema/comparisonAlignment.ts`, new — a second parallel path alongside `enumAlignment.ts`): `buildComparisonMatrixResult(perModel)` clusters the subject axis, the attribute axis, and (within each populated cell) the contributing models' values, each independently and each with a risk-calibrated matching bar:
- **Subjects** (product/option names) carry the highest risk — a false merge silently conflates two distinct real-world things (e.g. "iPhone 15" and "iPhone 15 Pro" are different products). The shared `textsAreNearDuplicates` helper can't be tightened enough to prevent this: its token-overlap signal is an overlap-coefficient (`overlap / min(lengthA, lengthB)`), which scores `1.0` for **any** subset relationship regardless of how high the threshold is set. Subject matching therefore disables that branch entirely (`tokenOverlapMin: 1.01`, mathematically unreachable) and relies only on a tight Levenshtein ratio (`0.15`, catching formatting/case/punctuation drift) plus a new `hasIdenticalTokenSet()` helper (`textSimilarity.ts`) that requires exact token-**set** equality — catching pure word-reordering ("Model 3 Tesla" vs "Tesla Model 3") without ever merging a superset name.
- **Attributes** (dimension labels like "battery life" vs "battery") reuse `enumAlignment.ts`'s existing item-label thresholds — a missed merge here just means an extra row, not a misattribution, so subset-tolerant matching is acceptable.
- **Values** (the cell content itself) are clustered only to classify agreement, never identity, so the loosest bar of the three is used.

Each cell's `agreement` is "consensus" when every contributing model's value clusters together, "majority" when the largest cluster exceeds half of contributing models, "split" otherwise, and "single_source" when only one model populated the cell; `consensusValue` (the modal/longest phrasing from the agreeing cluster) is set only for consensus/majority, since picking one value for a genuine "split" would misrepresent real disagreement. `verdictTally` counts each contributing model's `better`/`worse`/`even` call, when supplied.

Subjects and attributes covered by only 1-2 models move to `lowConfidenceSubjects`/`lowConfidenceAttributes` — the identical `>2`-model-panel refinement `ranked_enumeration` uses, applied to both axes independently. Cells for subject×attribute combinations no model ever populated are simply absent from `cells` — never fabricated as a filler "no data" entry; the renderer shows a plain "—" for those grid intersections instead.

**Prompt/validation**: `promptBuilder.ts` gained a `COMPARISON_CELL_INTERFACE` block plus an instruction to identify subjects/attributes directly from the question and to reuse the exact same subject/attribute string across all of a model's own cells (a within-response consistency requirement the model itself can satisfy, distinct from cross-model consistency, which the clustering above handles). `validator.ts` gained `ComparisonCellZod` with field-level salvage and value/rationale truncation, consistent with every other field type.

**Orchestration** (`lib/adaptiveSchema/orchestrate.ts`): `finalizeAdaptiveRun()` takes a second early, fully separate branch for `schema.id === "comparison_matrix"`, alongside `ranked_enumeration`'s — same reasoning: a comparison cell has no claim-matrix vocabulary equivalent, so `alignedClaims`/`gate`/`synthesisReport`/`trustSummary`/`rankedEnumeration` are all left `undefined` here too.

**Renderer** (`components/adaptive/ComparisonMatrixView.tsx`, new, wired into `AdaptivePanelResponse.tsx`'s `comparison_grid` branch): always shows a fixed honesty banner stating cell values are the panel's own generated assessments, not live verified pricing/spec data; renders a table with subjects as columns and attributes as rows, each cell showing the consensus/majority value with a coverage badge, or every contributing model's own differing value plus a "Models disagree" indicator for a split cell, or "—" for an unpopulated combination; renders low-confidence subjects/attributes inside separate collapsed `<details>` sections. Falls back safely to the legacy `AdaptiveResultsView` if `comparisonMatrix` is unexpectedly missing.

**Analytics**: `trackComparisonMatrixGap(...)` fires from the API route when the panel converges on fewer than 2 comparable subjects — the two-axis equivalent of `ranked_list_shortfall`, flagging a degenerate comparison outcome. Metadata only, never the raw question text.

**Classifier**: `comparison_matrix` moved from the "not yet supported" section of `classifierPrompt.ts` to the active section, with real decision criteria (two or more named things compared side by side across shared attributes, even a plain "X vs Y"; distinct from `ranked_enumeration`, an open-ended list ordered by one criterion rather than a grid of named things across multiple attributes, and from `contested_empirical`, where the disagreement between experts IS the answer rather than a factual side-by-side of named options).

Tests: `comparisonAlignment.spec.ts` (18 — independent subject/attribute clustering including the subset-merge guard, coverage math, all four agreement states, verdict tallying, the low-confidence bucket, never-padded missing cells, empty input), `ComparisonMatrixView.spec.tsx` (8 — structural renderer tests via `renderToStaticMarkup`, no jsdom), `comparisonMatrixOrchestration.spec.ts` (3 — end-to-end `finalizeAdaptiveRun` proving the parallel path never populates any other pipeline's fields).

#### `definition_explanation` activation (Milestone 2)

The third schema activated. Richer and more heterogeneous than the first two: 13 distinct top-level keys (vs. one repeated array field each for `ranked_enumeration`/`comparison_matrix`), covering every required intent — direct definition, beginner/general/expert explanation, concept distinction, analogy request, mechanism/process overview, term clarification, myth clarification, and role/responsibility explanation — through a single flat field list rather than per-intent branching.

**Types** (`lib/adaptiveSchema/types.ts`): `DefinitionDistinction` (`concept`/`explanation`), `DefinitionProcessStep` (`number`/`title`/`explanation`) → aggregated into `AggregatedDefinitionInterpretation` (`coverageCount`/`totalModels`/`coverageRatio`, `contributingModels`, and the full merged content: `term`, `directAnswer`, `explanation`, `keyPoints`, optional `example`/`analogy`/`advancedDetail`, `distinctions`, `processSteps`, `commonMisconceptions`, `relatedConcepts`, `sources`) → `DefinitionExplanationResult` (`primary`, `alternateInterpretations`, `isAmbiguous`, `sourceBacked`). Deliberately carries no single agreement/certainty score across interpretations — the product requirement is explicit that subjective wording differences must never be scored as if they were claim disagreement.

**One adaptation from the original product spec**: the recommended payload's nested `analogy: { text, limits }` object and top-level `meta: CommonResponseMeta` are not implemented as specified. `analogy` is two flat top-level fields at the per-model wire layer (`analogyText`/`analogyLimits`) — every other `FieldType` in this system is a plain string or an array of primitives, and a bespoke non-array nested-object field type would require touching `buildResponseZodSchema`/`salvageFields`' string-vs-array branching more invasively than this schema needs; the two fields are recomposed into the nested `analogy?: {text, limits}` shape the spec asked for, but only at the aggregation layer, where the merged result lives. `CommonResponseMeta` is skipped entirely, matching the precedent already set by `ranked_enumeration`/`comparison_matrix` (neither wired it in either) — this schema instead carries its own bespoke fields (`isAmbiguous`, `sourceBacked`) the same way those two carry `hasLiveQueryLogData`/`hasVerifiedSourceData`. Wiring `CommonResponseMeta` into exactly one of three parallel-path schemas would leave the architecture inconsistent; adopting it for all three is separate follow-up work, not a Milestone 2 requirement.

**Depth handling**: no new classification field was added. Unlike `ranked_enumeration`'s `requestedCount` (needed numerically by the aggregator to compute a shortfall), depth (beginner/general/expert) and style ("using a banking analogy") only affect the per-model prompt, so `promptBuilder.ts` instructs every model to detect them directly from the question's own phrasing rather than growing the shared `QueryClassification` contract for a concern this schema alone needs.

**Alignment/aggregation** (`lib/adaptiveSchema/definitionAlignment.ts`, new — a third parallel path): `buildDefinitionExplanationResult(perModel, totalModels)` clusters models by `directAnswer` similarity ONLY (the one field guaranteed to state what the term IS; `explanation` may elaborate very differently even when two models agree on the core answer) — models whose `directAnswer` clusters together become one interpretation; every other field is then merged within that cluster: `keyPoints`/`commonMisconceptions`/`relatedConcepts` via `textSimilarity.ts`'s existing `dedupeTextList`, `distinctions`/`processSteps` via bespoke concept/title clustering (keeping the longest `explanation` per merged item; process steps are renumbered sequentially afterward, since a cross-model merge can't preserve any one model's own numbering), `explanation`/`example`/`advancedDetail` by picking the longest non-"none" value (no prose-merging), and `analogyText`/`analogyLimits` kept paired from the same contributing model — never mixing one model's analogy with another's stated limitation. `totalModels` is passed explicitly rather than derived from `perModel`, since (unlike the other two schemas) a model that failed to parse has no fields object at all to include as an empty placeholder.

Models whose `directAnswer` does NOT cluster with the rest become `alternateInterpretations` instead of being merged away or discarded — this is the ambiguity-handling mechanism for terms with multiple accepted meanings (e.g. "What is a model?"). This module does not attempt to algorithmically distinguish "these models genuinely mean different domains" from "one model is simply wrong" — that judgment call is beyond what text-similarity clustering can honestly claim, so every multi-interpretation outcome is surfaced neutrally (`isAmbiguous: true`) rather than one being silently favored as ground truth. A complementary, earlier-stage safety net already exists at classification time: the classifier's existing `requiresClarification`/`clarificationQuestion` mechanism (unchanged, general-purpose since Milestone 1) can route a genuinely under-specified ambiguous question to a clarifying question before the panel ever runs, when there's truly no context to infer the intended domain.

**Prompt/validation**: `promptBuilder.ts` gained `DISTINCTION_INTERFACE`/`PROCESS_STEP_INTERFACE` blocks plus a depth/style/ambiguity-handling instruction gated on `schema.id === "definition_explanation"` (not a field-type check, since `term`/`directAnswer`/`explanation` are plain strings indistinguishable from any other schema's string fields). `validator.ts` gained `DistinctionZod`/`ProcessStepZod` with field-level salvage and nested `explanation` truncation, consistent with every other field type.

**Orchestration** (`lib/adaptiveSchema/orchestrate.ts`): `finalizeAdaptiveRun()` takes a third early, separate branch for `schema.id === "definition_explanation"` — only models that produced usable data are passed into aggregation (unlike the two array-field schemas, there's no natural "empty" placeholder for a whole missing object), with `alignedClaims`/`gate`/`synthesisReport`/`trustSummary`/`rankedEnumeration`/`comparisonMatrix` all left `undefined`.

**Renderer** (`components/adaptive/DefinitionExplanationView.tsx`, new, wired into `AdaptivePanelResponse.tsx`'s `definition_card` branch): strictly answer-first, in the required presentation order — direct answer, explanation, example/analogy (with a visually distinct limits callout directly beneath), distinctions/process steps, misconceptions, a collapsed `<details>` "Advanced detail" section, then a footer with related-concept badges, collapsible sources, and collapsible contributing-model chips. Shows an ambiguity banner plus a collapsed "Other meanings the panel found" section only when `isAmbiguous`. No Trust Summary, Agreement Map, or Panel Verdict Card — this schema never computes a claim-agreement score, so there is nothing genuine for a trust footer to summarize. Falls back safely to the legacy `AdaptiveResultsView` if `definitionExplanation` is unexpectedly missing.

**Analytics**: `trackDefinitionAmbiguity(...)` fires from the API route when `isAmbiguous` is true — the third schema-specific analytics event alongside `trackRankedListShortfall`/`trackComparisonMatrixGap`, all metadata-only (interpretation count), never raw question text.

**Classifier**: `definition_explanation` moved from the "not yet supported" section of `classifierPrompt.ts` to the active section, with decision criteria covering all ten required intents plus explicit boundary rules against every adjacent type: `factual_lookup` (single stable one-line fact vs. a concept that needs actual explanation), `causal_explanation` ("why does X happen" vs. "what IS X"/"how does X work" — a mechanism *overview* stays `definition_explanation` even though it explains a mechanism), `procedural`/`step_by_step_plan` (imperative instructions to follow vs. explanatory process steps for understanding), `comparison_matrix` (named things compared side by side vs. clarifying two related concepts), `claim_verification` (a myth-clarification question explaining a misconception vs. pressure-testing the user's own specific claim), and `current_live_information` (takes priority whenever the definition itself depends on right-now information).

Tests: `definitionAlignment.spec.ts` (12 — paraphrase merging, materially-different-interpretation preservation, sub-field merging, "none"-sentinel-to-undefined conversion, analogy/limits pairing, distinction/process-step merging with renumbering, source-backed detection, empty input), `DefinitionExplanationView.spec.tsx` (12 — structural renderer tests via `renderToStaticMarkup`, no jsdom, covering presentation order, every optional section, the ambiguity banner, and the explicit absence of Trust Summary/Agreement Map/Panel Verdict/claim matrix/generic-sections markup), `definitionExplanationOrchestration.spec.ts` (6 — end-to-end `finalizeAdaptiveRun` proving the parallel path never populates any other pipeline's fields, the coverage denominator uses all attempted models not just successful ones, and paraphrase-merging/ambiguity-preservation/"none"-sentinel-normalization all hold through the full `finalizeAdaptiveRun` call, not just at the unit level).

#### `causal_explanation` activation (Milestone 2)

The fourth schema activated. The central design risk this schema exists to guard against, stated explicitly in the approved spec and enforced at every layer below: **panel convergence is not causal proof**. Five models repeating the same causal story is evidence they agree, never evidence the story is true — so this schema computes no certainty/confidence score anywhere, and every "N of M models" figure is displayed as exactly that (panel agreement), never as a percentage of confidence.

**Wire-layer design**: every one of the 12 per-model fields is a plain `string` or `string[]` — `directAnswer`, `directCauses`, `contributingFactors`, `triggers`, `amplifiers`, `alternativeExplanations`, `causalLinks`, `confounders`, `disputedInterpretations`, `unknowns`, `testsOrEvidenceNeeded`, `sources`. Unlike the previous three schemas, this required **zero** new `FieldType`/Zod additions to `validator.ts` — the recommended payload's structured per-item objects (`CausalFactor`/`CausalLink`/`CausalInterpretation`, each with their own `evidenceStrength`/`sources`) are never collected at the wire layer at all; they're built entirely from these flat arrays at the aggregation layer, per the approved design's explicit instruction to prefer flat primitives over invasive validator changes.

**Types** (`lib/adaptiveSchema/types.ts`): `AggregatedCausalFactor` (`label`, `category`, `coverageCount`/`totalModels`/`coverageRatio`, `contributingModels`, `evidenceStrength`, `sourceBacked`), `AggregatedCausalLink` (a merged mechanism sentence, same coverage shape), `AggregatedCausalInterpretation` (`label`, `supportingModels` — never coverage-filtered), assembled into `CausalExplanationResult` (`directAnswer`, `factors`, `causalChain`, `confounders`, `disputedInterpretations`, `unknowns`, `testsOrEvidenceNeeded`, `sourceBacked`, `totalModels`). No certainty/confidence field exists anywhere in this type.

**Two adaptations from the recommended payload**, both because the wire layer intentionally has no per-item structure to draw from: (1) `CausalFactor.explanation` (a separate sentence from `label`) doesn't exist — each wire-layer string IS the full statement, label and explanation combined; (2) the recommended `modelCoverage?: Record<string, number>` top-level field is omitted — its intended meaning was underspecified (count of what, per model?) and `coverageCount`/`coverageRatio`/`contributingModels` already communicate panel convergence per factor/link, which is what actually matters here. `protective_factor` stays in the `CausalFactorCategory` vocabulary for completeness but no current wire field populates it (no model ever produces one today) — the same "documented, not fabricated" pattern as `bias_blindspot_audit`'s unexposed machinery.

**Alignment/aggregation** (`lib/adaptiveSchema/causalAlignment.ts`, new — a fourth parallel path): `buildCausalExplanationResult(perModel, totalModels)` clusters two structurally different kinds of text with two different bars:
- **Short causal-factor phrases** (`directCauses`/`contributingFactors`/`triggers`/`amplifiers`/`alternativeExplanations`): a *tighter* bar (`levenshteinMaxRatio: 0.25, tokenOverlapMin: 0.7`) than any other schema's short-label clustering, specifically because the approved design calls out "avoid merging causes merely because they share broad vocabulary" — two distinct causes that both happen to mention "the economy" must not collapse into one.
- **Full-sentence prose** (`causalLinks`' mechanism sentences, `disputedInterpretations`): the *looser* bar `definitionAlignment.ts` uses for `directAnswer` (`0.35`/`0.45`) — paraphrase drift over a full sentence produces a larger edit distance even when the meaning is identical.

Each of the 5 factor categories is clustered **separately** — a "direct cause" and a "contributing factor" naming the same real thing are never merged into one bucket, preserving exactly the distinction the schema exists to keep visible. `disputedInterpretations` are clustered and preserved in full, with **no low-confidence filtering** — unlike every other Milestone 2 schema's coverage-based low-confidence bucket, a minority causal interpretation raised by only one model is exactly what this field exists to keep from being silently dropped.

`evidenceStrength` is computed deliberately conservatively: "contested" only when the *same* factor is categorized differently by different models (some call it a direct cause, others an alternative explanation — a real, structurally detected disagreement, comparing like-length short phrases against each other), "unknown" otherwise. **A defect was caught and fixed before shipping**: an earlier version also cross-checked short factor phrases against `disputedInterpretations` (full sentences) for "contested" tagging — but the shared `textsAreNearDuplicates` overlap-coefficient scores close to 1.0 whenever a short phrase's few tokens all happen to appear somewhere in a much longer sentence, regardless of topical relevance (e.g. "Rising demand" would false-positive-match almost any dispute sentence containing both words "rising" and "demand" anywhere, about anything). This is exactly the "broad vocabulary" false-merge failure mode the design explicitly warns against, so that cross-check was removed; a regression test (`causalAlignment.spec.ts`) pins the correct non-match.

`sourceBacked` (both per-factor and result-level) is an explicit approximation, documented as such: true when a model that raised this factor *also* cited a source somewhere in its own response — the wire layer has no per-factor source attribution, so this can never mean the citation specifically supports that exact factor.

**Prompt**: `promptBuilder.ts` gained a 10-point instruction block (answer directly; separate direct causes from contributing factors; explain mechanisms, not correlations; identify confounders; include credible alternatives; distinguish established from disputed/speculative causes; avoid monocausal explanations for multi-causal issues; state what evidence would help; never treat sequence as proof; never overstate causality beyond what's supported), gated on `schema.id === "causal_explanation"` — plus an instruction to hold a higher evidence bar and say so explicitly for medical/legal/financial/public-policy topics.

**Orchestration** (`lib/adaptiveSchema/orchestrate.ts`): `finalizeAdaptiveRun()` takes a fourth early, separate branch, same "only successful models, explicit `totalModels`" pattern as `definition_explanation`.

**Renderer** (`components/adaptive/CausalExplanationView.tsx`, new, wired into `AdaptivePanelResponse.tsx`'s `causal_map` branch): direct answer, then main (direct) causes with distinct left-border treatment, contributing factors (triggers/amplifiers/protective factors folded into the same tier), a simple ordered causal-chain list (no graph/node editor), alternative explanations in a visually separate muted block, confounders, disputed interpretations in a distinct amber block with supporting-model chips, unknowns, evidence/tests needed, and a collapsed "Panel detail" section. Coverage badges always read "N of M models agree" — never a percentage or "confidence" label. A "Contested" badge appears only when the panel itself flagged disagreement. When `classification.riskLevel` is `safety_critical`/`high_stakes` (already computed for every classification since Milestone 1 — no new cross-cutting field needed), a human-review note is surfaced at the top. No Trust Summary, Agreement Map, Panel Verdict Card, or claim matrix.

**Analytics**: `trackCausalExplanationGap(...)` fires when either no direct causes survived validation or more than one disputed interpretation remains unresolved — metadata only (a reason enum), never raw question text.

**Classifier**: `causal_explanation` moved to the active section with decision criteria covering all ten supported question shapes plus explicit boundaries: `decision_support` (diagnostic-dominant vs. prescriptive-dominant intent in mixed questions like "why are signups falling, and what should we do"), `definition_explanation` ("why/how X leads to Y" vs. "what IS X"), `claim_verification` (explaining causation vs. pressure-testing the user's own specific causal claim), `comparison_matrix` (comparing named causal accounts side by side), `procedural`/`step_by_step_plan` (instructions vs. explanation), `current_live_information`/`data_analysis` (what changed vs. why it changed), and the protected high-stakes schemas (`medical_health`/`legal_regulatory`/`financial_valuation` keep their own existing criteria priority — `causal_explanation` is for general causal-mechanism questions outside those already-covered domains, not a replacement for them).

Tests: `causalAlignment.spec.ts` (18 — paraphrase merging, category isolation, mechanism clustering, alternative-explanation and disputed-interpretation preservation including minority explanations, confounder/unknown dedup, coverage math, source-backed aggregation, the "five models agreeing never upgrades evidenceStrength" safeguard, the "contested" category-conflict signal, and the false-positive regression above), `CausalExplanationView.spec.tsx` (15 — structural renderer tests covering presentation order, every section, the "models agree" (not confidence) coverage wording, the contested badge, collapsible panel detail, the high-stakes note, and the explicit absence of Agreement Map/Panel Verdict/claim matrix/generic-sections markup), `causalExplanationOrchestration.spec.ts` (9 — end-to-end `finalizeAdaptiveRun` proving the dedicated wire schema and `causalAlignment.ts` are used, no other pipeline's fields are populated, the coverage denominator uses all attempted models, and `factual_lookup`/`definition_explanation`/`decision_support`/`procedural`/the protected high-stakes schemas are all unaffected by this activation).

#### `checklist_taxonomy` activation (Milestone 2)

The fifth schema activated. Unifies two related request shapes behind one item structure rather than building two separate schemas: a plain **checklist** (order-independent items to consider/verify/gather — "give me a ransomware response checklist") and a categorized **taxonomy** ("what kinds of AI agents exist"). The distinguishing feature versus `ranked_enumeration`, this schema's closest sibling: **no `rank` field exists anywhere** — position in the list never implies importance or order.

**Types** (`lib/adaptiveSchema/types.ts`): `ChecklistItem` (per-model raw output: `id`, `label`, optional `category`/`rationale`/`critical`) → aggregated into `AggregatedChecklistItem` (`category` resolved to a canonical value or the `"General"` sentinel, `critical` as a majority vote, `coverageCount`/`totalModels`/`coverageRatio`, `contributingModels`) → grouped into `ChecklistCategoryGroup[]` → `ChecklistTaxonomyResult` (`summary`, `categories`, `lowConfidenceItems`, `notes`, `totalModels`). A single `"General"` category group is the signal the whole result should render as a flat checklist rather than a taxonomy with visible section headings — the renderer, not a separate flag, decides this from the data itself.

**Alignment/aggregation** (`lib/adaptiveSchema/checklistAlignment.ts`, new — a fifth parallel path, closest in shape to `enumAlignment.ts`): `buildChecklistTaxonomyResult(perModel)` clusters items via the same union-find + `textSimilarity.ts` machinery as `enumAlignment.ts` (identical `LABEL_DEDUP_THRESHOLDS`). The one deliberate design choice that inverts `causal_explanation`'s rule: items are clustered **across** category phrasing, not isolated per-category — a model that files "encryption at rest" under "Security" and another that files the identical item under "Technical" merge into one item, with the canonical category resolved by majority vote among contributing models. This is the opposite of `causal_explanation`'s factor clustering (there, a "direct cause" and a "contributing factor" naming the same thing must stay distinct) because here `category` is a loose, model-assigned grouping tag for what is still obviously the same real-world item, not a structural distinction the schema exists to preserve.

Items covered by only 1-2 models move to `lowConfidenceItems` — the identical `>2`-model-panel refinement `ranked_enumeration`/`comparison_matrix` use. `critical` is a majority vote among the models that raised the item (at least half flagged it critical), computed with the same "first occurrence per model wins" convention used for coverage tracking elsewhere — never inferred from how many models simply mentioned the item at all; coverage and criticality are tracked and reported as two entirely separate signals.

**Prompt/validation**: `promptBuilder.ts` gained a `CHECKLIST_ITEM_INTERFACE` block plus an instruction that list order never implies importance/sequence, `category` should only be set when the question genuinely asks for a taxonomy, and `critical` should be reserved for genuinely must-have items. `validator.ts` gained `ChecklistItemZod` with field-level salvage and rationale truncation, consistent with every other field type.

**Orchestration** (`lib/adaptiveSchema/orchestrate.ts`): `finalizeAdaptiveRun()` takes a fifth early, separate branch. Unlike `definition_explanation`/`causal_explanation` (which include only successful models plus an explicit `totalModels` parameter, since their per-model shape is a whole object with no natural "empty" placeholder), this schema follows `ranked_enumeration`/`comparison_matrix`'s convention instead: every model is included, with a failed model contributing an empty `items: []` via `extractChecklistFields`'s safe defaults — the core content here is an array field, so an empty array is already a meaningful, natural "this model contributed nothing" state.

**Renderer** (`components/adaptive/ChecklistTaxonomyView.tsx`, new, wired into `AdaptivePanelResponse.tsx`'s `checklist_taxonomy_view` branch): summary at the top, a notes callout when present, then either a flat checklist (no category headings, when the panel produced a single `"General"` group) or category-sectioned taxonomy (identical item rendering either way) — each item showing a checkbox-style marker, a "Critical" badge only for majority-flagged items, a coverage badge, optional rationale, and contributing-model chips. Low-confidence items render in a collapsed `<details>` section, same pattern as `RankedListView`. Falls back safely to the legacy `AdaptiveResultsView` if `checklistTaxonomy` is unexpectedly missing.

**Analytics**: `trackChecklistTaxonomyGap(...)` fires when the panel produced items but none survived into a main category group — every item ended up low-confidence, a degenerate "the panel couldn't converge on anything well-supported" outcome. Metadata only (a count), never raw question text.

**Classifier**: `checklist_taxonomy` moved to the active section with decision criteria covering both flavors (checklist and taxonomy) plus explicit boundaries: `ranked_enumeration` (an open-ended list where POSITION conveys importance/frequency — a request for "types/kinds of X" or items to verify stays `checklist_taxonomy` even when phrased with "top N" or "list", unless a genuine importance ranking is being requested), `comparison_matrix` (named things compared side by side vs. items/categories on their own), `definition_explanation` (one concept explained in depth vs. multiple items/categories enumerated), and `procedural`/`step_by_step_plan` (an ORDERED sequence of actions to perform vs. an order-independent checklist of things to verify/gather, even when both are phrased as "checklist for X").

Tests: `checklistAlignment.spec.ts` (14 — item clustering across category phrasing with majority-vote category resolution, the `"General"` sentinel for an uncategorized panel, taxonomy grouping when categories are present, the low-confidence bucket, critical majority-vote including the "minority flag doesn't count" case, notes/summary merging, empty input), `ChecklistTaxonomyView.spec.tsx` (9 — structural renderer tests covering the flat-vs-taxonomy rendering split, the critical badge, coverage badge, notes callout, collapsed low-confidence section, and the explicit absence of Trust Summary/Agreement Map/Panel Verdict/claim matrix markup), `checklistTaxonomyOrchestration.spec.ts` (3 — end-to-end `finalizeAdaptiveRun` proving the parallel path never populates any other pipeline's fields and that category grouping reaches the result correctly).

`capabilityGating.spec.ts` and `schemaRegistryStatus.spec.ts` updated for the current 15 active / 2 handoff / 11 disabled counts, with dedicated active-state assertions for `comparison_matrix`, `definition_explanation`, `causal_explanation`, and `checklist_taxonomy`.

#### `deep_research` activation (Milestone 2)

The sixth schema activated. Broad research synthesis across multiple subtopics/sources/frameworks — explicitly **not** a replacement for `contested_empirical` (kept active and completely unchanged): `contested_empirical` routes when the disagreement between experts IS the whole answer to a focused question; `deep_research` routes when breadth and synthesis are the dominant ask, of which disagreement (if present) is only one part of a fuller picture ("Do experts disagree on whether minimum wage raises unemployment?" stays `contested_empirical`; "Summarize the research on minimum wage and employment" is `deep_research`).

**Wire-layer design**: 8 flat fields — `executiveSummary` (string), `findings` (the one structured array field, `researchFinding[]` — a new dedicated type rather than reusing `claim[]`, since `Claim`'s stance/confidence vocabulary is built for a debate's claims, not a research finding's `category`/`evidenceStrength` shape), `disagreements`/`evidenceGaps`/`openQuestions`/`researchBoundaries`/`recommendedNextSteps`/`sources` (all plain `string[]`, following the approved "prefer flat fields, avoid deeply nested arbitrary JSON" instruction).

**Types** (`lib/adaptiveSchema/types.ts`): `ResearchFinding` (per-model raw output: `id`, `title`, `summary`, optional `category`/`evidenceStrength`/`sources`) → `AggregatedResearchFinding` (adds `sourceBacked`, `coverageCount`/`totalModels`/`coverageRatio`, `contributingModels`) → `DeepResearchResult` (`executiveSummary`, `findings`, `lowConfidenceFindings`, `disagreements` as `AggregatedResearchDisagreement[]`, `evidenceGaps`, `openQuestions`, `panelBlindSpots` as `AdaptiveCoverageGap[]`, `researchBoundaries`, `recommendedNextSteps`, `sourceCoverage`, `totalModels`). `evidenceStrength` reuses `causal_explanation`'s `CausalEvidenceStrength` vocabulary directly (`"strong" | "moderate" | "weak" | "contested" | "unknown"`) rather than duplicating an identical union under a new name.

**Infrastructure reuse — a real refactor, not just a new file**: the approved design explicitly asked to reuse the existing three-tier Bias & Blind Spots system for `panelBlindSpots` ("detect when all models omit the same important dimension"). Tier 2 already existed (`coverageAudit.ts`'s `auditPanelCoverage` — a dedicated Gemini call auditing what the panel, taken together, never addressed) but its signature took `rows: AlignedClaim[]` and only ever read `.claimText` off each row. Since `deep_research`'s findings are a `ResearchFinding[]`, never `AlignedClaim[]`, the signature was broadened to `claimTexts: string[]` — a mechanical, behavior-preserving change (the function's logic is unchanged; only its input shape got more general). The one existing call site (`synthesisReport.ts`) was updated to `rows.map(r => r.claimText)`, and its own test file (`coverageAudit.spec.ts`) was updated to pass plain strings instead of building fake `AlignedClaim` fixtures. This makes `auditPanelCoverage` genuinely schema-agnostic — reusable by any future schema's own unit of content, not just the claim-matrix pipeline's rows.

**Alignment/aggregation** (`lib/adaptiveSchema/deepResearchAlignment.ts`, new — the sixth parallel path, and the only `async` one in Milestone 2, since it awaits a real model call): `buildDeepResearchResult(perModel, question)` clusters `findings` on `summary` text using the same prose-length bar `causalAlignment.ts`/`definitionAlignment.ts` use for full sentences (looser than short-label clustering — paraphrase drift over a sentence produces a larger edit distance even when the meaning is identical). Category is resolved by majority vote across a cluster, the same "loose grouping tag, not a structural distinction" treatment `checklist_taxonomy` gives its items — unlike `causal_explanation`'s categories, which must never blur. `disagreements` cluster the same way and are **never coverage-filtered** — a minority disagreement raised by only one model is exactly what this field exists to keep visible, mirroring `causal_explanation`'s `disputedInterpretations`. Findings covered by only 1-2 models (panel > 2 models only) move to `lowConfidenceFindings`, the same threshold rule every Milestone 2 schema shares.

`evidenceStrength` follows the same design discipline as `causal_explanation`: defaults to `"unknown"` regardless of how many models raised a finding, flipping to `"contested"` only on a genuine independent signal (the finding also matches a clustered disagreement, or any contributing model already self-reported `"contested"`) — five models repeating the same finding never upgrades it to `"strong"`. `sourceBacked` is computed per-finding more precisely than `causal_explanation`'s response-level approximation, since `ResearchFinding.sources` genuinely exists at the wire layer: true when the finding itself carries sources, OR (falling back to the same approximation `causal_explanation`/`definition_explanation` use) when a contributing model's overall response-level `sources` array is non-empty. `sourceCoverage` (`findingsWithSources`/`totalFindings`/`coverageRatio`) is computed directly from all findings (main + low-confidence) — no `sourceTypes` breakdown by source type (primary/review/commentary/etc.) is computed, since the wire layer only captures a plain source label, not a type tag; adding that would require either unreliable NLP classification or a deeper wire schema than the approved flat-fields instruction allows. `panelBlindSpots` is populated by directly calling the (now-generalized) `auditPanelCoverage(question, "deep_research", allFindings.map(f => f.summary))` — degrading to `[]` on any failure per that function's own long-standing contract, never invented.

**Prompt**: `promptBuilder.ts` gained a `RESEARCH_FINDING_INTERFACE` block plus a 10-point instruction block (identify major dimensions; concise executive summary; separate established from disputed findings; identify evidence gaps; preserve materially different interpretations; state research boundaries/scope limits; never imply exhaustiveness; distinguish primary evidence/reviews/commentary/speculation; flag outdated evidence/time-window ambiguity; suggest high-value follow-ups), gated on `schema.id === "deep_research"` — plus source-grounded-mode guidance: if the user asked to use only specific provided sources and the model cannot verify it's actually restricted to them, say so plainly in `researchBoundaries` rather than silently supplementing with training knowledge (this codebase has no real document-ingestion/source-restriction infrastructure today, so honesty here is the only available safeguard — not a real enforcement mechanism).

**Orchestration** (`lib/adaptiveSchema/orchestrate.ts`): `finalizeAdaptiveRun()` takes a sixth early, separate branch — the only one that's awaited for a genuine async reason beyond the function's own existing `async` signature. Every model is included (a failed model contributes empty defaults), matching `ranked_enumeration`/`comparison_matrix`/`checklist_taxonomy`'s convention.

**Renderer** (`components/adaptive/DeepResearchView.tsx`, new, wired into `AdaptivePanelResponse.tsx`'s `deep_research_view` branch): executive summary first, then grouped findings (category headings when the panel provided more than one category, a flat list otherwise — same pattern as `ChecklistTaxonomyView`), a separate amber-toned disagreements section, a compact source-coverage stat line, evidence gaps, open questions, an expandable "Panel blind spots" section (Tier 2 gaps, with `dimension`/`whyItMatters`/`followUpQuestion`), research boundaries, recommended next steps, and a collapsed "Panel detail" footer. Coverage badges always read "N of M models agree" — never a percentage or "confidence" label, same discipline as `CausalExplanationView`. No Trust Summary, Agreement Map, Panel Verdict Card, or claim matrix as the primary view.

**Analytics**: `trackDeepResearchGap(...)` fires when the synthesis came back genuinely thin — either no finding has any source support, or source coverage is below 25% — metadata only (a reason enum), never raw question text.

**Classifier**: `deep_research` moved to the active section with decision criteria covering all ten supported intents plus explicit boundaries against every adjacent type, most importantly `contested_empirical` (whose own bullet was also updated with a direct cross-reference and worked example, per the approved relationship rules), and also `causal_explanation` (one causal question vs. a broad "what are the causes of X" synthesis), `definition_explanation` (one term vs. many subtopics), `comparison_matrix` (named things compared vs. broader landscape synthesis), `claim_verification` (pressure-testing one stated assertion, even about research/causation, vs. synthesizing what the research broadly says), and `ranked_enumeration`/`checklist_taxonomy` (when a ranked-list or checklist/taxonomy shape is explicitly requested instead of a synthesized narrative).

Tests: `deepResearchAlignment.spec.ts` (16 — paraphrased-finding merging, distinct-dimension preservation, disagreement preservation including a single-model minority position, the low-confidence bucket, gap/open-question dedup, per-finding and response-level-fallback source-backed aggregation, model-coverage math, the reused Tier-2 audit surfacing a real panel omission and degrading safely on failure, the "five models agreeing never upgrades evidenceStrength" safeguard, the "contested" independent-signal check, no certainty score anywhere, empty/malformed input — `callGemini` mocked at the connector level for the audit call, same convention as `classifierV2.spec.ts`/`coverageAudit.spec.ts`), `DeepResearchView.spec.tsx` (10 — structural renderer tests covering presentation order, every section, the "models agree" coverage wording, the expandable blind-spots section, and the explicit absence of a generic shell/claim-matrix/Panel-Verdict/certainty-percentage), `deepResearchOrchestration.spec.ts` (8 — end-to-end `finalizeAdaptiveRun` proving the dedicated wire schema and `deepResearchAlignment.ts` are used, no other pipeline's fields are populated, and `contested_empirical`/`causal_explanation`/`definition_explanation`/`comparison_matrix`/`factual_lookup` are all unaffected by this activation). Also updated: `coverageAudit.spec.ts` (mechanical fixture change for the broadened `auditPanelCoverage` signature — same 5 tests, same assertions, no behavior change).

`capabilityGating.spec.ts` and `schemaRegistryStatus.spec.ts` updated for the current 16 active / 2 handoff / 10 disabled counts, with a dedicated active-state assertion for `deep_research`.

#### `evidence_review` activation (Milestone 2)

The seventh schema activated. Evaluates **how strong/credible/reliable a body of evidence, a study, a source, or a methodology is** — a meta-evaluation of evidence QUALITY itself, distinct from both its closest siblings: `deep_research` synthesizes substantive findings across a topic ("what does the research say"); `evidence_review` evaluates the evidence/study/source itself ("how good IS this evidence"), which may be about a specific document without the user asserting any claim as their own ("How credible is this earnings-call transcript's growth claim?").

**Wire-layer design**: 7 flat fields — `overallAssessment` (string), `dimensions` (the one structured array field, `evidenceDimension[]` — each a quality dimension like methodology, sample size, conflicts of interest, replication status, source credibility, or generalizability, with its own model-asserted `strength`), `redFlags`/`strengths`/`applicabilityCaveats`/`recommendedChecks`/`sources` (all plain `string[]`).

**Types** (`lib/adaptiveSchema/types.ts`): `EvidenceDimension` (per-model raw output: `id`, `dimension`, `assessment`, optional `strength`) → `AggregatedEvidenceDimension` (adds `coverageCount`/`totalModels`/`coverageRatio`, `contributingModels`) → `EvidenceReviewResult` (`overallAssessment`, `overallStrength`, `dimensions`, `lowConfidenceDimensions`, `redFlags`, `strengths`, `applicabilityCaveats`, `recommendedChecks`, `sourceBacked`, `totalModels`). `strength`/`overallStrength` reuse `causal_explanation`'s `CausalEvidenceStrength` vocabulary directly, the third schema to do so (after `deep_research`).

**The central design risk, stated explicitly in code comments throughout**: evidence being widely repeated is not evidence of it being good. Every `strength` value — per-dimension and overall — is derived from the panel's OWN judgments about evidence quality, never from how many models simply participated.

**Alignment/aggregation** (`lib/adaptiveSchema/evidenceReviewAlignment.ts`, new — the seventh parallel path): `buildEvidenceReviewResult(perModel, totalModels)` clusters `dimensions` on their `dimension` label using the same tight, "avoid merging on shared broad vocabulary" bar `causalAlignment.ts` uses for short factor labels ("Sample size" and "Sample selection bias" must stay distinct dimensions, not collapse into one). Per-dimension `strength` is derived from the FIRST-OCCURRENCE-PER-MODEL set of that dimension's own self-reported strength values: "unknown" when no contributing model reported one, the shared value when every model that reported one agrees, and **"contested" when models' own quality judgments genuinely conflict** (e.g. one model reads a sample as "weak," another reads the same dimension as "strong") — never derived from coverage count, mirroring `causal_explanation`'s discipline exactly. `overallStrength` is then a genuine roll-up of the aggregated dimensions' own strengths (excluding "unknown"): "contested" if any dimension is itself contested or the dimensions disagree with each other, the shared value if they agree, "unknown" if no dimension carries a real signal — never a popularity count. Dimensions covered by only 1-2 models (panel > 2 models only) move to `lowConfidenceDimensions`, the same threshold rule every Milestone 2 schema shares. `redFlags`/`strengths`/`applicabilityCaveats`/`recommendedChecks` merge via the same list-dedup helper used throughout Milestone 2.

**One bug caught and fixed before shipping**: the first draft of `buildEvidenceReviewResult` filtered to only successful models before aggregating (matching `definition_explanation`/`causal_explanation`'s "whole-object, no natural empty placeholder" convention) but forgot to also thread an explicit `totalModels` parameter through — meaning failed models would have silently disappeared from the coverage denominator instead of being counted, undercounting exactly the "honest denominator" every other Milestone 2 schema is careful to preserve. Caught during implementation (before any test ran) by comparing against `causalAlignment.ts`'s actual signature; fixed by adding the explicit `totalModels` parameter (defaulting to `perModel.length` for callers with nothing to filter), with the real orchestration call site passing the full attempted count explicitly. A dedicated regression test (`evidenceReviewAlignment.spec.ts`) now pins the correct behavior.

**Prompt**: `promptBuilder.ts` gained an `EVIDENCE_DIMENSION_INTERFACE` block plus a 7-point instruction block (direct overall assessment first; break the review into only the quality dimensions that actually matter, not a rote checklist; give an honest per-dimension strength read — never inflate because evidence merely exists; name concrete red flags without softening them; name concrete positive credibility signals; state generalizability limits; suggest what a careful reader should still verify), gated on `schema.id === "evidence_review"`, closing with an explicit reminder that popularity/repetition is never proof of quality.

**Orchestration** (`lib/adaptiveSchema/orchestrate.ts`): `finalizeAdaptiveRun()` takes a seventh early, separate branch — synchronous (no model call, unlike `deep_research`'s reused Tier-2 audit) — filtering to successful models with an explicit `totalModels` parameter, matching `causal_explanation`'s exact convention.

**Renderer** (`components/adaptive/EvidenceReviewView.tsx`, new, wired into `AdaptivePanelResponse.tsx`'s `evidence_review_view` branch): the overall assessment and its strength badge first (answer-first), then the quality-dimension breakdown (each with its own strength badge — omitted entirely for "unknown," since there's nothing meaningful to show — and a "models agree" coverage badge, never a percentage), red flags in a distinct red-toned block, positive strengths, applicability caveats, recommended checks, and a collapsed "Panel detail" footer. A high-stakes human-review note surfaces automatically from `classification.riskLevel` (the same pattern `CausalExplanationView` established — no new cross-cutting field needed). No Trust Summary, Agreement Map, Panel Verdict Card, or claim matrix.

**Analytics**: `trackEvidenceReviewGap(...)` fires when `overallStrength` comes back `"weak"` or `"contested"` — metadata only (the strength value itself), never raw question text.

**Classifier**: `evidence_review` moved to the active section with decision criteria covering all ten acceptance categories (evidence strength, clinical/policy evidence, source credibility, survey methodology, meta-analysis trust, vendor white-paper reliability, dataset support, benchmark meaningfulness, breaking-news evidence) plus explicit boundaries against `deep_research` (quality of the evidence vs. what it concludes), `causal_explanation` (how good the evidence for a causal claim is, not the mechanism itself), `claim_verification` (evaluating evidence/methodology quality, which can be about a specific document, vs. pressure-testing the user's own stated belief), and `definition_explanation`. Risk level flows through unchanged — a clinical/legal/financial/safety-critical evidence review gets `riskLevel` `safety_critical`/`high_stakes` like any other classification, which is what the renderer's human-review note reads.

Tests: `evidenceReviewAlignment.spec.ts` (16 — paraphrased-dimension merging, distinct-dimension preservation, strength derived from model self-reports (agreement/contested/unknown), the "five models repeating 'weak' never upgrades it" safeguard, the derived `overallStrength` roll-up in all three states, the low-confidence bucket, red-flag/strength/caveat/check dedup, source-backed aggregation, the fixed coverage-denominator bug, empty/malformed input), `EvidenceReviewView.spec.tsx` (10 — structural renderer tests covering answer-first order, strength and coverage badges, the contested badge appearing only on genuine model disagreement, red flags/strengths/caveats/checks, collapsible panel detail, the high-stakes note, and the explicit absence of a generic shell/claim-matrix/Panel-Verdict), `evidenceReviewOrchestration.spec.ts` (7 — end-to-end `finalizeAdaptiveRun` proving the dedicated wire schema and `evidenceReviewAlignment.ts` are used, no other pipeline's fields are populated, the coverage denominator uses all attempted models, and `deep_research`/`causal_explanation`/`factual_lookup` are unaffected by this activation).

`capabilityGating.spec.ts` and `schemaRegistryStatus.spec.ts` updated for the current 17 active / 2 handoff / 9 disabled counts, with a dedicated active-state assertion for `evidence_review`.

#### `bias_blindspot_audit` activation (Milestone 2)

The eighth schema activated, and architecturally the most different from the other seven: it doesn't compute anything new so much as **expose the three-tier Bias & Blind Spots system already embedded in every synthesis report** (`biasDetection.ts`/`coverageAudit.ts`/`diagnostics.ts`, built during the earlier Synthesis Report Polish work) through a dedicated, standalone query type. The embedded behavior inside `synthesisReport.ts` is completely untouched — this activation reuses the exact same functions, not a fork or a reimplementation.

**Reused versus new, by tier**:
- **Tier 1 (attributed model-specific bias)** — 100% reused, zero changes: `detectAdaptiveBiases` (`biasDetection.ts`) already took raw `ModelResult[]` and a `schemaId: QueryType` string, so it was schema-agnostic before this activation even started. `bias_blindspot_audit`'s own wire-layer schema deliberately has **no** `attributedBiases` self-report field — a flat string without the excerpt-evidence requirement `detectAdaptiveBiases` already enforces could never meet the "do not accuse a model of bias based on weak inference" bar, so Tier 1 has exactly one source, never two competing ones.
- **Tier 2 (panel-level omissions)** — reused via `auditPanelCoverage` (`coverageAudit.ts`), the same function `deep_research` generalized from `AlignedClaim[]` to plain `string[]`. Called here as an independent second-opinion audit over the panel's own per-model summaries, then merged with the panel's own self-reported `omittedDimensions` — overlapping entries (by text similarity) keep the audited gap's `whyItMatters`/`followUpQuestion` and note both signals in a `coverageReason` string (e.g. "identified by independent coverage audit and raised by 2 of 4 models"); self-report-only entries get a plain "raised by N of M models" reason.
- **Tier 3 (structural diagnostics)** — **new**, not a reuse of `diagnostics.ts`'s `computeAdaptiveDiagnostics`: that function is built from `AlignedClaim[]`'s `agreementScore`/`evidenceType`, neither of which this parallel path ever produces (it never goes through claim alignment at all). `bias_blindspot_audit`'s own Tier 3 computes citation coverage, source concentration, and — the one deliberately reused piece — a homogeneity flag using the exact same `HOMOGENEITY_AGREEMENT_THRESHOLD` constant the embedded system uses, even though the underlying signal necessarily differs (clustering models' own summaries for near-duplication, since there's no `agreementScore` here to threshold directly).

**Renderer reuse**: `BiasFindingCards` (`AdaptiveSynthesisReportView.tsx`) was exported (a minimal, additive change — just the `export` keyword, verified behavior-unchanged against its own existing test suite) and imported directly into the new `BiasBlindspotAuditView.tsx` for Tier 1, since this schema's `attributedBiases` is the exact same `AdaptiveBiasFinding[]` shape. `CoverageGapCard`/`DiagnosticsStrip` were **not** reused — this schema's Tier 2 (`AggregatedPanelBlindSpot`, with a `coverageReason` the embedded `AdaptiveCoverageGap` doesn't have) and Tier 3 (source-concentration/geographic-bias split) shapes are intentionally richer, so force-fitting them into components built for the narrower embedded types would have been more invasive than writing small, focused renderers that share the same visual language instead.

**Types** (`lib/adaptiveSchema/types.ts`): `AdaptiveBiasFinding`/`BiasEmptyReason` reused verbatim for Tier 1. New: `AggregatedPanelBlindSpot` (Tier 2), `BiasStructuralDiagnostics`/`BiasSourceConcentration` (Tier 3), and `BiasBlindspotAuditResult` assembling all three tiers plus `sharedAssumptions`/`missingStakeholders`/`followUpQuestions`. **No new `FieldType` was needed at all** — every one of the 9 wire-layer fields is a plain `string`/`string[]`, the simplest wire schema of any Milestone 2 activation (Tier 1's richer shape lives entirely on the reused-function side, never touching the per-model prompt contract).

**The central safeguard, enforced structurally, not just in prose**: an empty Tier 1 is never rendered as "no bias exists." `BiasBlindspotAuditResult.biasEmptyReason` is populated (reusing `BiasEmptyReason`'s existing vocabulary) whenever `attributedBiases` is empty, and the renderer shows "No model-specific bias was confidently attributable" plus an explicit "this does not mean the answer is unbiased" caveat — Tier 2 and Tier 3 render completely independently of Tier 1's outcome.

**A real bug caught and fixed during implementation** (found while writing the renderer, not by a failing test — worth calling out since it reflects a design gap, not a typo): the first draft gated the entire view behind a `hasAnyContent` check that only looked at `summary`/Tier 2/Tier 3/assumptions/stakeholders — it forgot that Tier 1's own "no attribution" message is itself meaningful content the spec requires to always render, so a run with genuinely nothing else to show would incorrectly fall through to a generic blank-state message instead of Tier 1's explanatory one. Fixed by making the true "nothing at all" empty state trigger only on `totalModels === 0` (no models were ever attempted) — Tier 1's section, and its no-attribution fallback text, now always renders whenever the schema ran at all. A related fix landed in the same pass: the citation-coverage badge no longer counts a trivial "0 of N models cite a source" stat as meaningful Tier 3 content on its own.

**A second bug caught while writing tests** (test-infrastructure, not production code): the two reused tier calls run in `Promise.all`, and `auditPanelCoverage` silently skips its network call entirely when it has no claim texts (e.g. every model's `summary` is empty in a fixture). A first draft of the test mocks used a FIFO `mockResolvedValueOnce` queue assuming both calls always fire in order — when one call was skipped, its queued mock leaked, unconsumed, into the next test and misaligned that test's queue (the same class of bug as the classifier's documented LRU-cache test-carryover lesson, just for mock queues instead of a cache). Fixed by routing the mock's response based on request CONTENT (a substring check on the system prompt distinguishing the bias-detection call from the coverage-audit call) instead of call order — immune to either call being skipped.

**Prompt**: `promptBuilder.ts` gained a 10-point instruction block (distinguish model-specific bias, which needs the separate dedicated evidence-based check, from shared panel omissions; never label ordinary disagreement as bias; never infer ideological motive without evidence; name specific missing dimensions, not vague statements; name affected stakeholders specifically; identify shared assumptions; identify source/evidence-type concentration while keeping geographic concerns separate; distinguish geographic/institutional bias from a plain factual error; suggest precise follow-up questions; admit when no genuine gap exists rather than inventing one), gated on `schema.id === "bias_blindspot_audit"`, closing with explicit "no invented bias, no unsupported political labeling, no demographic inference, no generic boilerplate" guardrails.

**Orchestration** (`lib/adaptiveSchema/orchestrate.ts`): `finalizeAdaptiveRun()` takes an eighth early, separate branch — the second (after `deep_research`) to await real model calls, this time TWO run in parallel via `Promise.all` inside `biasBlindspotAlignment.ts`. It's also the only branch that threads the RAW `results: ModelResult[]` parameter through (not just validated `adaptiveResults`) — Tier 1 needs full raw response text, which no other Milestone 2 schema's aggregation has ever needed.

#### `decision_support` activation (Milestone 2)

The ninth schema activated, from the user's own detailed specification. Helps the user choose, prioritize, approve, defer, escalate, or decide among concrete options under uncertainty — the first Milestone 2 schema whose central output is a **recommendation**, not just a synthesized/clustered view of the panel's raw content, which makes "never let model popularity become the recommendation" (this schema's version of the design discipline every prior Milestone 2 activation has enforced for evidence/causality) the single hardest requirement to get right structurally, not just rhetorically.

**Wire-layer design**: 15 fields, mostly flat per the approved design. Two new, deliberately shallow `FieldType`s: `decisionAssessment[]` (`{id, optionLabel, criterionLabel, assessment, evidenceStrength?}`, cross-referencing `options`/`criteria` by exact string reuse rather than nesting) and `decisionRisk[]` (`{id, label, likelihood?, impact?, mitigation?, optionLabel?}`). `userProvidedCriteria` is a subset-marking field (not a per-criterion property) so the aggregation layer can tag each merged criterion's provenance without a third wire field per criterion. **Two deliberate deviations from the user's recommended `DecisionCriterion`/`DecisionAssessment` shape, both documented in `types.ts`, not silently dropped**: no numeric `weight` on criteria and no numeric `score` on assessments — either would imply a false precision this system's honesty discipline avoids everywhere else (the same reasoning behind `CausalEvidenceStrength`'s qualitative-only vocabulary, reused here). `DecisionCriterion.source` is simplified from the recommended three-way `user`/`inferred`/`model` to a two-way `user`/`model` — a flat wire-layer self-report can't reliably distinguish "inferred from context" from "purely model-generated," so claiming that distinction would be manufacturing a signal that doesn't really exist.

**Alignment** (`lib/adaptiveSchema/decisionSupportAlignment.ts`, new — explicitly **not** reusing claim alignment, per the user's direct instruction): options and criteria are each an independently clustered axis, architecturally the same "two-axis grid" shape `comparisonAlignment.ts` established for subjects × attributes. Options reuse that file's exact `subjectsMatch`-style matcher (tight Levenshtein + `hasIdenticalTokenSet`, subset-containment merging disabled) since options are named real-world things where a false merge ("HubSpot Marketing Hub" absorbing "HubSpot Sales Hub") would silently misattribute one option's assessment to another; criteria use the tighter "short-label" bar `causalAlignment.ts` established for factor labels. Each raw `DecisionAssessment`/`DecisionRisk`'s free-text `optionLabel`/`criterionLabel` is resolved against the canonical clusters via a shared `resolveCluster()` helper — a reference that doesn't match any known option/criterion is **dropped**, never used to fabricate a new axis entry (the same "never invent a missing cell, and never invent a new row/column either" discipline `comparisonAlignment.ts` established, extended to also guard the axes themselves). Missing option×criterion cells are simply absent from `assessments`, never padded with fabricated placeholder text.

**The recommendation — the central piece of this activation**: each contributing model's own `recommendationAction` is parsed defensively (case/hyphen/space-normalized against the 7-value enum; unparseable text contributes no vote at all, never a fabricated default). When every contributing model's action agrees, that shared action is used as-is. **The moment models genuinely disagree on the action — or agree on `choose_option` but name different options — the aggregate never becomes a majority vote.** It falls back to a conservative action (`escalate` if any model itself said `escalate`, otherwise `defer`; `choose_option` with disagreeing options downgrades to `conditional_go` with `recommendedOptionId` left unset) and the rationale/caveats state the split explicitly (e.g. "2 of 3 recommend go; 1 of 3 recommends no go") rather than hiding it behind a single confident-looking sentence. `supportCount`/`totalModelsWithRecommendation` report this convergence for transparency only — the exact same "coverage is not a certainty score" convention every prior Milestone 2 schema uses for its own coverage counts, just applied to a recommendation instead of a claim/finding/factor. `humanReviewNeeded` is a **real, computed field** (not left to the renderer to infer from a separate `riskLevel` prop the way `CausalExplanationView`/`EvidenceReviewView` do) — true when `classification.riskLevel` is high-stakes/safety-critical, when the recommendation is contested, when more than half of the recommended option's own assessments carry weak/contested/unknown evidence strength, or when the action itself is `escalate`/`defer`.

**Prompt**: `promptBuilder.ts` gained `DECISION_ASSESSMENT_INTERFACE`/`DECISION_RISK_INTERFACE` blocks plus a 12-point instruction block (state the decision plainly; identify real options, never invented ones; distinguish user-stated from added criteria; never invent a user preference/weighting that wasn't given; surface missing information rather than deciding for the user; surface real risks even when recommending an option; prefer a reversible low-regret step under uncertainty; use `conditional_go` rather than false confidence; avoid one universal recommendation when scenarios genuinely differ — use `sensitivityFindings` instead; state what would change the recommendation; escalate high-stakes decisions the available evidence can't responsibly resolve; prefer `defer`/conditional framing over guessing when decision-critical information is missing), gated on `schema.id === "decision_support"`, closing with the same "never let model popularity become the sole basis of the recommendation" instruction given directly in the user's spec.

**Orchestration** (`lib/adaptiveSchema/orchestrate.ts`): `finalizeAdaptiveRun()` takes a ninth early, separate branch — synchronous, filtering to successful models with an explicit `totalModels` parameter (matching `causal_explanation`/`evidence_review`'s convention for rich, heterogeneous per-model objects with no natural "empty" placeholder). `classification?.riskLevel` is threaded through as a third argument to `buildDecisionSupportResult` specifically so `humanReviewNeeded` can be computed honestly inside the alignment layer, not bolted on afterward.

**Renderer** (`components/adaptive/DecisionSupportView.tsx`, new, wired into `AdaptivePanelResponse.tsx`'s `decision_support_view` branch): a human-review amber note (when `humanReviewNeeded`) first if applicable, then the decision question as compact framing directly above the recommendation badge (recommendation-first, per the spec's explicit UI requirement, while still literally preceding it with the decision question per the spec's own recommended section order), the "Panel split" indicator when contested, rationale and caveats, a plain-text "N of M models converged on this — not a certainty score" line (never a percentage), options considered, a decision-criteria × options matrix (missing cells render as `—`, never fabricated, reusing `ComparisonMatrixView.tsx`'s exact table-scroll pattern), risks and tradeoffs in a red-toned block, assumptions, uncertainties (in a distinct callout — missing information is never hidden), sensitivity findings ("what would change this recommendation"), a reversible-next-step callout, and a collapsed "Panel detail" footer. No claim matrix, Panel Verdict Card, generic research shell, or fabricated numeric decision-certainty score anywhere.

**Analytics**: three events — `trackDecisionSupportContested` (the aggregate recommendation was genuinely contested, with the resulting conservative action), `trackDecisionSupportHighSensitivity` (at least one sensitivity finding was produced), `trackDecisionSupportMissingCriteria` (at least one genuine decision-critical uncertainty was surfaced — distinct from the pre-execution `requiresClarification` path, which is already tracked generically by the existing `query_clarification_requested` event and needed no new plumbing for this schema). All metadata only (counts/enum values), never raw rationale/finding text.

**Classifier**: `decision_support` moved to the active section with decision criteria covering all six given acceptance categories (vendor selection, go/no-go, initiative prioritization, build-or-buy, escalation, incomplete-data recommendations) plus explicit boundaries against `comparison_matrix` (compares without necessarily recommending), `ranked_enumeration` (ranks an open-ended list, doesn't choose among a constrained set), `causal_explanation` (explains why, doesn't prescribe what to do — mirrors the boundary rule already written into `causal_explanation`'s own entry when it was activated, now completed from this side), `procedural`/`step_by_step_plan` (explain how to carry out an already-chosen action), `scenario_analysis` (currently disabled — explores forward conditions without necessarily recommending), `financial_valuation` (stays the routing target when valuation metrics dominate, not decision_support), and `claim_verification` (verifying a stated claim vs. choosing an action). The missing-criteria requirement from the user's spec is handled entirely through the **existing, general-purpose** `requiresClarification`/`clarificationQuestion` classification-level mechanism — no new plumbing needed, same reuse pattern `definition_explanation`'s ambiguity handling established for genuinely irreducible cases.

#### Phase 0 audit + Phase 1 persistence (2026-07-28 → 2026-07-29)

A full requirement-by-requirement audit of the query-routing redesign against its original spec, followed by the first of several planned post-Milestone-2 phases. Full detail lives in two dedicated documents, not duplicated in full here:

- `docs/query-routing-completion-audit.md` — the Phase 0 audit (per-requirement status/evidence/remaining-work table across classifier, registry, renderers, persistence, governance, observability, protected paths, and the 200-row matrix), plus a Phase 1 completion addendum.
- `docs/adaptive-persistence-design.md` — the Phase 1 design (current run-document shape, write/read lifecycles, Firestore size assessment for the 4 heaviest schemas, the storage-location decision, and post-build implementation confirmation).

**What Phase 0 found, concretely:** the classifier/registry/routing core was solid and matched the spec closely, but two things assumed by later phases were false: adaptive schema output (any of the 9 Milestone 2 result shapes, `classification`, `CommonResponseMeta`) was never persisted to Firestore at all — a Milestone-2 run only existed in the browser tab that produced it — and governance was hard-wired to a legacy `runType: "research" | "verification" | "video"` model with zero awareness of the 28-type taxonomy.

**What Phase 1 built** — a durable, versioned persistence layer for the 9 active Milestone 2 schemas, and `CommonResponseMeta` wired consistently across all of them. Deliberately did NOT touch governance, peer review, decision receipts, export, classifier behavior, routing behavior, or any of the 10 legacy-active schemas' persistence path — those are Phase 2 or explicitly out of scope.

**`CommonResponseMeta` — extended, not duplicated.** The type already existed (`types.ts`) but was only ever populated by `commonMeta.ts::buildCommonMeta()`, called exclusively from `routeClassifiedQuery.ts` for non-execution responses (handoff/disabled/clarification/unanswerable). Rather than introduce a second, differently-shaped type under the same name for the new execution-metadata fields the phase's own spec wanted (`totalModels`, `successfulModels`, `failedModels`, `modelsWithUsableOutput`, `sourceCoverage`, `executionStatus`), the existing interface gained those fields as pure additions — all optional, since they're meaningful only for an actual execution and non-execution responses simply never populate them. Two fields were deliberately NOT added under new names because an equivalent already existed: `requiresHumanReview` reuses the existing `humanReviewNeeded`; the recommended `schemaId` field was added (the existing `queryType` covers classification-level identity; `schemaId` matches `AdaptivePanelResult`'s own established name for "which schema actually ran"). `limitations: string[]` is new and deliberately distinct from the existing `uncertainties`/`blindSpots` — those carry a schema's own self-reported content (e.g. `decision_support`'s own `uncertainties` list); `limitations` carries meta-level statements about THIS RESULT's completeness/provenance (e.g. "1 of 2 selected models did not produce usable structured output"), computed by the new builder, never by a schema's own prompt.

**One shared builder** (`lib/adaptiveSchema/commonResponseMeta.ts::buildCommonResponseMeta()`), called once per schema branch inside `orchestrate.ts::finalizeAdaptiveRun()` via a single new helper, `attachAdaptiveEnvelope()` (9 one-line call sites, not 9 reimplementations). Honest model counting: `totalModels` = every selected model regardless of outcome; `successfulModels` = connector status `"ok"`/`"substituted"`; `failedModels` = the difference; `modelsWithUsableOutput` = models that ALSO passed adaptive schema validation — a connector success carrying malformed JSON does not count. `executionStatus` is `"completed"` only when every selected model both succeeded and produced usable output, `"failed"` only when zero usable output exists at all, `"partial"` otherwise — never derived from model agreement.

**Source coverage adapters** (`getAdaptiveSourceCoverage`), one branch per schema, using each schema's own real answer units where they exist (`ranked_enumeration` items, `comparison_matrix` cells, `definition_explanation` interpretations, `causal_explanation`/`deep_research` factors/findings via their existing per-unit `sourceBacked` approximation, `bias_blindspot_audit`'s existing Tier 3 citation-coverage stat) and falling back to the schema's own response-level `sourceBacked` boolean — never a fabricated unit-level ratio — for the three schemas with no per-unit source signal at all (`checklist_taxonomy`, `evidence_review`, `decision_support`).

**Human-review adapter** (`getAdaptiveHumanReviewSignals`): `high_stakes`/`safety_critical` riskLevel always triggers it; beyond that, each schema reuses its OWN already-computed signal where one exists (`decision_support`'s own `humanReviewNeeded` is reused verbatim, never recomputed) or a schema-specific real signal (`definition_explanation.isAmbiguous`, a `causal_explanation` factor marked `"contested"` or a disputed interpretation, `evidence_review.overallStrength` weak/contested, `comparison_matrix` majority-low-confidence subjects). Explicitly never triggered by model count/agreement alone — a dedicated test proves a 2-of-5-models-succeeded run does NOT set it when nothing else signals review.

**Limitations adapter** (`getAdaptiveLimitations`): concrete, computed, per-schema statements (existing shortfall notes, missing-cell counts, dispute/ambiguity flags, `decision_support`'s own recommendation caveats plus an inferred-vs-user-provided-criteria check), deduplicated by exact string match (these are programmatically generated, not model prose, so the fuzzy near-duplicate merging `textSimilarity.ts` uses elsewhere isn't needed) — plus one universal statement the shared builder itself adds when `modelsWithUsableOutput < totalModels`.

**The versioned envelope** (`lib/adaptiveSchema/persistedOutput.ts`): `PersistedAdaptiveOutputV1`, a 9-variant discriminated union keyed by `schemaId`, each carrying `version`, `answerShape` (verified against the real `SCHEMA_REGISTRY` renderHints, not invented), `classification`, `meta`, `result`, `generatedAt`. Runtime validation (`parsePersistedAdaptiveOutput`) is deliberately NOT a full Zod re-derivation of all 9 already-complex result types — that would be pure duplicated maintenance burden for data this codebase's own alignment functions already validated once, at generation time. Instead: a lightweight structural check per schema (the specific fields each renderer actually destructures, with the right JS type), checking version, schemaId/answerShape agreement, and schemaId/result shape agreement, returning one of four states (`ok: true` / `"absent"` / `"unsupported_version"` / `"malformed"`) and never throwing.

**Firestore persistence** (`lib/firestore/runs.ts::persistAdaptiveOutput()`): embedded on the run document (`runs/{runId}.adaptiveOutput`), not a subcollection — the design doc's size assessment (computed from each schema's own `maxItems`/`maxWords` registry caps) showed even the largest schema's worst case (`comparison_matrix`, ~50-60 KB, the biggest because cells retain a per-model value map) is under 10% of the existing 850 KB document-size safety budget already established for raw per-model text. Guarded by the SAME `estimateDocumentSize`/`MAX_TOTAL_DOC_SIZE` machinery `completeRun()` already uses; if ever exceeded, the write OMITS `adaptiveOutput` rather than failing the run (mirrors the existing "degrade gracefully" posture for `perModel` truncation). Written additively, in the same request, immediately after `finalizeAdaptiveRun()` succeeds — never a retry job, never a second model call, never a second quota charge (quota is charged once, at `checkAndIncrementUsageForRun()`, entirely before this write). A write failure is caught, logged (metadata only), and never fails the run response — the live `adaptiveOutput` was already computed in memory and is returned either way, with a `persistenceStatus: "saved" | "failed" | "omitted_size_limit" | "not_applicable"` response field reflecting what happened. `"omitted_size_limit"` is deliberately its own state, not folded into `"failed"` (added right after Phase 1's initial build, per explicit review feedback) — a size-guard omission is an expected, deterministic outcome of that run's own content, while `"failed"` means a genuine write error worth investigating if it recurs; conflating the two would make `"failed"` both over-broad and useless as an alert signal.

**API surface**: `app/api/run-panel/route.ts`'s response gains `adaptive.adaptiveOutput?: PersistedAdaptiveOutputV1` (the stable envelope) and `adaptive.persistenceStatus`. The existing many-optional-fields pattern (`rankedEnumeration`, `decisionSupport`, etc.) remains for backward compatibility but is now derived from the same `finalizeAdaptiveRun()` call, not an independent source of truth. `GET /api/user/panel-history` gains two summary-only fields per research item (`hasAdaptiveOutput`, `adaptiveSchemaId`) — reads only the envelope's discriminator, never the full `result`/`meta`, keeping the list response light. `GET /api/user/runs/[runId]` runs the persisted `adaptiveOutput` through the real validator and returns `{ status: "valid" | "absent" | "malformed" | "unsupported_version", output }`.

**Client restoration**: a new pure adapter (`lib/user/adaptivePersistedOutputAdapter.ts::adaptPersistedOutputToPanelPayload()`) maps a validated envelope to the exact `AdaptivePanelPayload` shape a LIVE run already produces — history restoration reaches the correct dedicated renderer through `AdaptivePanelResponse.tsx`'s existing, UNCHANGED schemaId/answerShape routing, no duplicated renderer-selection logic. `results: []` is deliberate (no per-model raw adaptive data is persisted, and none of the 9 dedicated renderers read that field when their own named result is present). Wired into `app/page.tsx`'s `openHistoryItem`: `"valid"` restores the adaptive panel; `"absent"` (the normal case for pre-Phase-1 runs) silently falls back to the existing legacy raw-model rendering, unchanged; `"malformed"`/`"unsupported_version"` show a small non-blocking amber notice rather than an error, and also fall back to legacy rendering. Reload never reclassifies the question and never calls `runPanel()`.

Under-teaching the classifier to "protect" it from disabled types would just make those questions silently misclassify as `generic` instead of correctly routing to `graceful_limitation`.

#### Phase 2A — governance, peer review, and decision receipts (2026-07-29, Steps 1-6)

Full detail lives in `docs/governance-decision-receipts-design.md`, not duplicated in full here — this is a short pointer summary.

**What Step 1's audit found:** two entirely separate, pre-existing legacy governance systems — System A (`lib/governance/evaluateGovernance.ts`, org-wide automated policy, triggered only from `/api/synthesize-panel`) and System B (`lib/governance/teamGovernancePipeline.ts`, per-team policy + a single-reviewer peer-review flow). Step 1 believed neither was ever triggered for adaptive (Milestone 2) runs, citing `app/page.tsx`'s "skipped entirely for adaptive runs" comment — **this was later found to be only partially true (see Step 6 below): that comment covers one of two client-side triggers, not both.**

**What Steps 2-4 built** (all inert/unreferenced by any runtime path until Step 5C): `GovernanceRecordV1` and `AdaptiveDecisionReceipt` (`lib/adaptiveSchema/governanceRecord.ts`) — a new, additive, schema-aware contract intended for `runs/{runId}.governanceRecord`, deliberately never touching System A/B's own fields; `buildAdaptiveDecisionReceipt()` (`lib/adaptiveSchema/decisionReceiptBuilder.ts`) — one pure, deterministic builder dispatching to 9 per-schema receipt builders, reshaping each schema's own result into a uniform 8-field receipt (never re-clustering or inventing content); `parseGovernanceRecord`/`canRefreshDecisionReceipt`/`applyHumanReviewUpdate` (`lib/adaptiveSchema/governanceRecordParser.ts`) — runtime validation, a pure refresh-eligibility rule (`pending` is a new Phase 2A state, not inherited from System B, and is refreshable), and a pure human-review-update helper that never mutates its input or regenerates the receipt.

**What Step 5 built and wired live:** `initializeAdaptiveGovernanceRecord()` (`lib/adaptiveSchema/governanceInitialization.ts`) — builds and persists a new `GovernanceRecordV1` only when none exists yet, never rebuilds an existing one (reviewed or not), never calls a model/classifier; `persistGovernanceRecord()`/`readGovernanceRecordForInitialization()` (`lib/firestore/runs.ts`) — a second, independent additive Firestore write (`runs/{runId}.governanceRecord`, `{merge:true}`), deliberately separate from `persistAdaptiveOutput()` so a governance-record problem can never take down an already-successful adaptive-output write. **Step 5C wired this into `app/api/run-panel/route.ts`**: after `persistAdaptiveOutput()` succeeds (never before, never when it failed or was size-omitted), the route reads any existing `governanceRecord`, then calls the initializer, and surfaces a compact `adaptive.governanceInitializationStatus` field on the response (`"created" | "already_exists" | "blocked_reviewed" | "not_applicable" | "malformed_existing_record" | "unsupported_existing_version" | "omitted_size_limit" | "failed" | "skipped_adaptive_not_saved"`) — never receipt content, never a raw error, never able to suppress the adaptive answer or change HTTP success behavior. A read failure, AND an unexpectedly missing run document, are both never treated as "no record exists" — the two started out conflated in the first draft (a missing run could otherwise have let `persistGovernanceRecord`'s `{merge:true}` write create an orphan `runs/{runId}` doc), caught in review and split into a distinct `"run_missing"` state before this step was approved; both have dedicated tests.

**Still not wired, deliberately**: System A automated evaluation into `automatedGovernance`, System B/`teamRuns` integration, the peer-review API, a governance dashboard, history UI display of `governanceRecord`, export, and receipt refresh (the `canRefreshDecisionReceipt` rule exists but nothing calls it yet).

**Step 6 — System A audit and a confirmed, now-fixed blocker.** Auditing System A's 8 rules (`docs/governance-decision-receipts-design.md` §14.2) found only 3-4 are safe to reuse against adaptive data as-is (source-completeness, model-failure-count, and the consensus-score rule's own honest null-handling) — two rules would misbehave silently if wired against adaptive data without redesign (one produces a misleading reason string from a coerced `null→0`; one is a permanent no-op against a hard-coded placeholder field). Separately, and more urgently: the audit's trace of the actual client call graph — later confirmed by executing the real `/api/synthesize-panel` route against adaptive-shaped input in a test — found that **adaptive runs COULD already reach legacy claims-matrix synthesis and System A governance**, via two unguarded triggers in `app/page.tsx` (`generateSynthesisAutomatically`'s two call sites, plus one unguarded `synthesizeReport()` call on history reload) and a total absence of adaptive-awareness in `/api/synthesize-panel/route.ts` itself. This has been fixed: client-side guards on all three gaps (mirroring the one correct guard that already existed, both on the live-run path and in `components/ResultsDisplay.tsx`'s own independent trigger), plus an authoritative, durable-data-based server-side rejection (`parsePersistedAdaptiveOutput` against `runs/{runId}.adaptiveOutput`, never a client-supplied flag) that rejects with `409 ADAPTIVE_RUN_NOT_SUPPORTED`/`ADAPTIVE_RUN_INVALID`/`ADAPTIVE_RUN_UNSUPPORTED_VERSION` before any LLM call, write, or governance evaluation — and, per a post-review correction, `503 RUN_LOOKUP_UNAVAILABLE` (fails CLOSED, never falls through to legacy synthesis) if the run lookup itself can't be completed, since that lookup is what determines whether the request is safe to process at all. Existing runs that were already polluted before this fix are not migrated in this step.

**Step 6B — adaptive automated governance, designed then implemented, now LIVE.** A new, additive evaluator (`lib/governance/evaluateAdaptiveGovernance.ts`) reuses only 2 of System A's 8 rules against real adaptive data — source-completeness (limited to the 3 schemas with real per-unit source tracking: `ranked_enumeration`/`comparison_matrix`/`definition_explanation`) and model-failure count (all 9 schemas), both via the SAME `GovernancePolicy` fields System A already reads. Consensus, substitution, sensitive-domain, and evidence-quality rules are excluded outright — no real adaptive equivalent exists for any of them, and none is fabricated. Wired into `app/api/run-panel/route.ts` immediately after Step 5C's governance initialization: evaluates once per run (never automatically re-evaluates an existing result), persists via a NEW nested Firestore field-path write (`governanceRecord.automatedGovernance`/`governanceRecord.updatedAt` only — never a whole-record rewrite), specifically so a concurrent human reviewer's decision can never be clobbered by a stale automated pass (verified by a dedicated concurrency regression test). Surfaces a compact `adaptive.automatedGovernanceStatus` field, separate from `governanceInitializationStatus`. `evaluateGovernance.ts` and its 3 legacy callers remain completely untouched. System B, `teamRuns`, reviewer APIs, the dashboard, history UI, export, an explicit reevaluation endpoint, and `admin_audit_logs` integration for adaptive runs all remain unimplemented.

**Step 7, Part A/B — System B audit and adaptive team-review design (read-only/design only).** Auditing System B (`lib/governance/teamGovernancePipeline.ts`, `lib/teams/*`, `app/api/teams/*`) found: a team-scoped policy engine whose 3 rules all require a `ConsensusSummary` no adaptive schema produces; a `teamRuns` collection that is the ONLY canonical location for legacy `TeamRunHumanDecision` decisions (an unconditional `.update()`, no terminal-state protection, no transaction); and zero UI consumer anywhere in `app/`/`components/` (`GovernanceDashboard.tsx` is exclusively System A's). Design settled on `governanceRecord.humanReview` (not `teamRuns`) as the canonical adaptive review state, with `teamRuns` becoming a queue PROJECTION only — and, per an explicit correction, the new adaptive review path must enforce terminal-state protection and prevent concurrent double-review overwrites from the start, unlike System B's own legacy behavior. Full detail: `docs/governance-decision-receipts-design.md` §20/§21.

**Step 7, Part D — transaction-safe adaptive human review, now LIVE.** A new dedicated route, `POST /api/teams/adaptive-runs/{runId}/decision`, submits a terminal review decision (`approved`/`approved_with_conditions`/`changes_requested`/`rejected`) for an adaptive run. Reuses System B's exact authorization mechanism (`getRequestUid`/`loadUserAndTeam`/`isTeamAdmin`) with no new auth path, and the deterministic `teamRuns` projection lookup as the primary tenant-isolation mechanism (stored fields checked defensively too — a forged/malformed projection fails closed). The canonical write, `submitAdaptiveHumanReview()` (`lib/firestore/runs.ts`), uses a REAL Firestore transaction (`adminDb.runTransaction()`) — reads the current `governanceRecord` inside the transaction, checks the caller's `expectedUpdatedAt` against the live `updatedAt` (optimistic concurrency) BEFORE checking whether the current `humanReview.status` is still reviewable (a new `isHumanReviewStatusReviewable()` predicate, `lib/adaptiveSchema/governanceRecordParser.ts` — terminal statuses are genuinely terminal, unlike System B's own legacy route), then writes ONLY `governanceRecord.humanReview`/`governanceRecord.updatedAt` via nested field paths, identical in spirit to Step 6B's own nested-write pattern. After the canonical transaction commits — and only after — the `teamRuns` projection is synced (status/timestamp fields only, best-effort, never rolling back the canonical decision on failure) and a `human_review_decided` governance event is written to the same `governanceEvents` subcollection Step 6B already uses (metadata only: reviewer uid, prior/new status, team/schema/answerShape — never comment, conditions, or receipt content). Once the transaction commits, the route always returns HTTP 200; a projection-sync or event failure is reflected only in a `projectionSyncStatus` response field or server logs, never an error status. `policyEngine.ts`, `teamGovernancePipeline.ts`, and the legacy `teamRuns/{runId}/decision` route remain completely untouched. **Still not wired**: any list endpoint, dashboard, review UI, reviewer assignment, multiple reviewers, review history, reopening terminal reviews, comment threads, quorum, export support for adaptive rows, or `admin_audit_logs` integration (Part E, if ever built). Full detail: `docs/governance-decision-receipts-design.md` §23.

**Step 7, Part E1 — adaptive team-review queue API and read-only UI, now LIVE (read-only — no decision form yet).** Corrects a live gap this step's own audit found (§24.1): adaptive `teamRuns` projections were already flowing through the legacy `GET /api/teams/runs` endpoint, untagged and commingled with legacy rows. A new, opt-in versioned contract (`?version=1`) returns `{ok, version: 1, items: TeamRunListItemV1[], pagination}`, where every item is explicitly `{kind: "legacy"}` or `{kind: "adaptive"}` (`lib/governance/teamRunListContract.ts`). A strict classifier (`classifyTeamRunRow()`) never lets a malformed adaptive row fall back to the legacy mapper — a wrong/missing required adaptive field is skipped and logged (metadata only), never silently reinterpreted. The legacy default (unversioned) response is completely unchanged — no internal consumer of it was found anywhere in `app/`/`components/`/`hooks/` (reconfirmed, not assumed). A new read-only detail endpoint, `GET /api/teams/adaptive-runs/{runId}` (`lib/governance/adaptiveReviewDetail.ts`), reuses Part D's authorization/projection-lookup pattern and always reads the canonical parent `governanceRecord` — a projection/parent mismatch is logged, never repaired inline, never trusted over the parent. A brand-new, READ-ONLY System B UI ships at `/team/reviews` (queue) and `/team/reviews/{runId}` (detail) — deliberately separate from the existing System A `/governance` dashboard, which remains untouched. The UI renders no Approve/Request-Changes/Reject control and calls no POST route at all, verified by a dedicated source-level structural test. The legacy audit-export route now explicitly excludes adaptive rows by their real `adaptive` discriminator, rather than the previous accidental protection of them merely lacking legacy columns. No cursor pagination and no new Firestore index were introduced — the existing in-memory, full-team-scan read/sort/paginate pattern is deliberately preserved, since no composite `teamRuns` index exists and a server-side `.orderBy()` without one would silently fail. **Still not built**: the decision form itself, any UI mutation call, reviewer assignment, multiple reviewers, review history, reopening, comment threads, quorum, adaptive export, `admin_audit_logs` integration, and indexed cursor pagination (Part E2, not started). Full detail: `docs/governance-decision-receipts-design.md` §25.

**Step 7, Part E2 — adaptive review decision form and mutation UX, now LIVE. The Phase 2A adaptive governance product workflow is now complete end-to-end.** The existing `/team/reviews/{runId}` page gained a real decision form, submitting to the EXISTING, completely unmodified Part D route (`POST /api/teams/adaptive-runs/{runId}/decision`) — no new API surface was added. Client validation (`lib/governance/adaptiveReviewFormContract.ts`) calls the REAL server parser (`parseAdaptiveReviewDecisionRequest()`, Part D) directly rather than re-implementing its rules — verified to have no `server-only` guard or Node-only dependency anywhere in its chain, so this is a single shared implementation, not two kept in sync by convention. The form supports all 4 terminal decisions (`approved`/`approved_with_conditions`/`changes_requested`/`rejected`), enforces the same comment/condition limits as the server (4,000/20/500), and always sends the most recently fetched canonical `updatedAt` as `expectedUpdatedAt` — never a value from `teamRuns`. Submission (`lib/client/adaptiveReviewSubmission.ts`) makes exactly one POST, with no automatic retry under any circumstance (stale conflict, terminal conflict, network failure, or server error all require an explicit user action first). A successful canonical commit is always treated as success even when `projectionSyncStatus` comes back `"failed"` — shown with a restrained, non-alarming notice, never implying the decision itself failed. Stale and terminal conflicts each show a distinct message and a "Reload Review" action that refetches canonical detail — the form disappears entirely if the reloaded record is now terminal. The queue page needs no new code to refresh on return, since its existing Part E1 fetch-on-mount effect already covers it. Manual browser verification was genuinely performed for the auth/team-gating states (using a real signed-in session); the full authorized approve/conflict flow was not manually exercised (disclosed explicitly — would require creating real team/run data) but is fully covered by an automated end-to-end contract test exercising the real detail and decision routes together. **Still not built**: reviewer assignment, multiple reviewers, review history, reopening terminal decisions, comment threads, quorum, adaptive export, `admin_audit_logs`, indexed cursor pagination, automated-governance reevaluation, and receipt refresh. Full detail: `docs/governance-decision-receipts-design.md` §26.

**Immutable Adaptive Review History and Admin Audit Integration, now LIVE.** Every successfully committed adaptive review decision now produces two additional, best-effort, independently-idempotent artifacts AFTER the canonical `governanceRecord.humanReview` transaction commits (which remains completely unchanged and still the sole canonical CURRENT state): an immutable history record at `runs/{runId}/humanReviewHistory/{decisionId}` (metadata only — decision status, reviewed time, whether a comment was present, condition count — never comment/condition text, receipt content, or reviewer name) and a genuinely idempotent entry in the existing org-wide `admin_audit_logs` collection (`action: "adaptive_human_review_decided"`, written via `.doc(` `` `adaptive-review:${decisionId}` `` `).create()`, unlike the legacy `writeAuditEvent()` helper, which has always used a random, non-idempotent `.add()`). `decisionId` is a deterministic SHA-256 hash of `teamId+runId+reviewedAt+newStatus`, computed at the route layer entirely after the transaction commits — chosen specifically to avoid touching Part D's already-shipped `GovernanceRecordV1`/`applyHumanReviewUpdate()` schema and its wide existing test coverage. A critical audit finding was resolved before implementation: the existing admin-audit READER (`/api/governance/audit`) has a hard-coded action allowlist that would have silently dropped the new action entirely — fixed additively, with zero effect on any existing action's behavior. A new read-only endpoint, `GET /api/teams/adaptive-runs/{runId}/history`, and a "Review History" section on the detail page expose this — never reviewer identity, comment, conditions, or a decision/team ID. An internal, not-yet-exposed `repairAdaptiveReviewArtifacts()` service can backfill a missing history/audit record for an already-terminal decision without ever reopening the review or touching the canonical record. **Still not built**: reviewer assignment, multiple reviewers, review history editing, reopening, comment threads, quorum, adaptive export, indexed cursor pagination, automated-governance reevaluation, and receipt refresh. Full detail: `docs/governance-decision-receipts-design.md` §27.

**Single-Reviewer Assignment for Adaptive Human Review (Part E3), now LIVE.** An already-authorized team `owner`/`admin` may now optionally assign exactly one eligible reviewer (`owner`/`admin` — this codebase's membership model has no `inactive`/`removed`/`pending` state, confirmed by audit, so eligibility reduces to the same two roles the existing decision-submission gate already accepts) to a pending adaptive run, via `GET/PUT/DELETE /api/teams/adaptive-runs/{runId}/assignment`. Assignment lives entirely separately from the canonical `governanceRecord.humanReview` — a new, single-fixed-ID, `revision`-guarded document at `runs/{runId}/humanReviewAssignment/current` (`lib/governance/adaptiveHumanReviewAssignment.ts`, `submitAdaptiveHumanReviewAssignment()` in `lib/firestore/runs.ts`) — and never grants review-submission permission by itself; the assignee must still independently pass the existing `isTeamAdmin` gate. The decision route (`POST .../decision`) gained the smallest possible additive check, immediately after that existing gate: if a reviewer is assigned, only that reviewer or a team OWNER (a deliberately narrower override than the `owner`/`admin` assignment-mutation tier, so it stays a genuine escape hatch rather than a routine bypass on multi-admin teams) may submit — anyone else gets a clear `403 reviewer_assigned`, never a concealing `404`. The assignment transaction re-reads `governanceRecord.humanReview.status` fresh on every call (the same pattern Part D's own transaction uses), which closes the race between a concurrent decision-completion and an in-flight assignment mutation by construction — once terminal, assignment becomes permanently read-only (`409 not_pending`). A metadata-only, create-only `humanReviewAssignmentHistory` subcollection and three new idempotent `admin_audit_logs` actions (`adaptive_human_review_reviewer_assigned`/`_reassigned`/`_unassigned`) are wired through the exact additive allowlist mechanism the History step established — never reviewer email, display name, comments, or decision content; display names are resolved at READ time only (`users/{uid}.name`, else the existing `maskEmail()` helper). A compact "Reviewer" section on the existing `/team/reviews/{runId}` page shows the current assignee, an "Assigned to you" indicator, management controls while pending, and a fixed read-only notice once terminal. An internal, not-yet-exposed repair service exists with one honestly disclosed limitation: it cannot reconstruct which reviewer preceded the current one for any assignment past its first-ever mutation, and reports that limitation rather than guessing. **Still not built**: multiple reviewers, reviewer groups, quorum, comments/discussion threads, reopening, escalations, notifications, due dates, workload balancing, auto-assignment, and automatic governance reevaluation on reassignment. Full detail: `docs/governance-decision-receipts-design.md` §28.

**Multi-Reviewer and Quorum Governance — architecture, ARCHITECTURE PORTION DESIGN-ONLY (votes/aggregation/finalization/UI), FOUNDATION PORTION NOW LIVE (Part B, see below).** A complete architecture for extending the above single-reviewer model to a governed multi-reviewer panel with quorum-based finalization has been designed and documented. Recommended shape: run-scoped subcollections `runs/{runId}/humanReviewPanel/current` (mutable, revision-guarded panel config — **now implemented**, see the Part B paragraph below), `runs/{runId}/humanReviewVotes/{panelRevision}:{reviewerUserId}` (one immutable, create-only vote document per reviewer — never an array inside one mutable document, which cannot give per-reviewer immutability at the database layer — **not yet implemented**), and `runs/{runId}/humanReviewPanelHistory/{eventId}` (**not yet implemented**). A single deterministic, versioned aggregation engine (parameterized by panel size and an approval threshold) is designed to subsume "any one reviewer," "majority," and "unanimous" as presets of the same algorithm — **not yet implemented**. `governanceRecord.humanReview` remains the sole canonical final state, and remains completely untouched by every part of this feature built so far. Migration strategy: coexistence via a new team-level opt-in flag, never automatic conversion or backfill — every existing team keeps today's exact single-reviewer behavior forever unless explicitly enabled (**this part is now live**, see below). Full detail, including the panel/vote contracts, the full aggregation truth tables, the authorization/privacy matrices, and a 5-part phased implementation plan (Parts B–F): `docs/governance-decision-receipts-design.md` §29.

**Multi-Reviewer Panel Foundation, Storage, and Coexistence (Part B), now LIVE.** The panel-configuration foundation from the architecture above is implemented — panel schema/storage/reconfiguration and coexistence detection only; **votes, aggregation, quorum completion, finalization, owner override for panel outcomes, panel history, and any multi-reviewer UI still do not exist anywhere in this codebase.** A team must explicitly opt in via a new `adaptiveMultiReviewerSettings` field on `TeamDocument` (absent/disabled for every existing team — fail-closed parser, no migration, no UI to set it yet) before a team `owner`/`admin` may create a panel via `GET/PUT/DELETE /api/teams/adaptive-runs/{runId}/review-panel`, backed by a new `runs/{runId}/humanReviewPanel/current` document (mutable, `revision`-guarded, `status: "open"|"cancelled"` only — no `"finalized"`/`"ready_to_finalize"` value exists in the type at all yet). The critical piece: the existing decision route (`POST .../decision`) gained a **fail-closed** panel-presence gate, ordered before the existing (fail-OPEN) single-reviewer assignment check — an OPEN panel now blocks direct decision submission with `409`, and a panel-lookup infrastructure failure ALSO blocks it with `503` — the deliberate opposite of how the existing single-reviewer assignment lookup behaves on an identical read failure, since a panel represents a stronger governance commitment that must never be silently bypassed by an outage. A cancelled panel restores the single-reviewer path exactly as it was; the panel document itself is never physically deleted. **Operational hazard, explicitly disclosed**: creating a real panel today makes that run's direct decision route permanently blocked until the still-unbuilt vote/finalization capability (Parts C–E) ships — no team should actually use this endpoint for a real run yet, even though it is fully functional. Full detail: `docs/governance-decision-receipts-design.md` §30.

**Immutable Multi-Reviewer Vote Contract and Submission (Part C), now LIVE.** A listed panel reviewer may now cast exactly one immutable vote per panel revision via `POST/GET /api/teams/adaptive-runs/{runId}/votes`, backed by a new `runs/{runId}/humanReviewVotes/{voteId}` subcollection (one create-only document per `(panelRevision, reviewerUserId)` pair, deterministic ID `r{revision}:{encodeURIComponent(reviewerUserId)}`). **Aggregation, quorum completion, panel finalization, owner override for panel outcomes, vote editing/withdrawal, and any multi-reviewer UI still do not exist anywhere in this codebase.** A vote is create-only and permanently immutable: an exact resubmission is idempotent (returns the original vote, unchanged), a differing resubmission is rejected as a conflict, and one reviewer can never overwrite another's vote (independent documents at independent deterministic IDs). The submission transaction re-reads the parent run, `governanceRecord` (must still be reviewable), the panel (must be open, revision must match, caller must be listed), and — deliberately, unlike Part B's lighter panel-mutation pattern — the TEAM document itself, fresh, inside the same transaction, to re-verify the caller is still a current, eligible team member at the exact moment of write, since a cast vote can never be undone. Vote comment/conditions validation reuses the EXACT same rules, limits, and normalization as the existing single-reviewer decision route (extracted into one shared pure function rather than forked, verified behavior-preserving against that route's own pre-existing test suite). Privacy: full vote text (comment/conditions) is visible only to the vote's own author — nobody else, including the team owner, sees another reviewer's comment or conditions in this step (a deliberate narrowing from the original architecture's owner-visibility exception, per this step's own more conservative instruction). Full detail: `docs/governance-decision-receipts-design.md` §31.

**Pure Multi-Reviewer Aggregation Engine and Quorum Truth Tables (Part D), now LIVE — as a pure function only, NOT WIRED TO ANY ROUTE.** `aggregateAdaptiveReviewVotes()` (`lib/governance/adaptiveReviewAggregation.ts`) is a standalone, zero-I/O, independently testable pure function that consumes a panel configuration and its current-revision votes and reports quorum/majority status — `"waiting"` (below quorum), `"deadlocked"` (quorum met, no strict majority in either the approval group `{approved, approved_with_conditions}` or the blocking group `{changes_requested, rejected}`), `"ready"` (a deterministic terminal outcome, a supporting-reviewer UID set, and condition-COUNT-only metadata — never condition text), or `"invalid"` (12 distinct, deterministic reasons, never a thrown exception). A group wins only with a strict majority of SUBMITTED votes, never of total reviewers or the quorum value; within a winning group, any `approved_with_conditions` vote escalates the result and any `rejected` vote escalates it, but a losing minority group's votes never override the winner (no rejection veto). As of Part E (below), this function is now actually wired to a real finalization transaction — no owner override and no multi-reviewer UI exist yet. Full detail: `docs/governance-decision-receipts-design.md` §32.

**Transactional Multi-Reviewer Finalization, History, Audit, Events, and Repair (Part E), now LIVE.** `POST /api/teams/adaptive-runs/{runId}/review-panel/finalize` transactionally finalizes a `ready` multi-reviewer panel into the canonical `governanceRecord.humanReview` — the first real write path for the Part D aggregation engine. The finalization transaction re-reads and re-validates the run, panel, and every current-revision vote fresh (vote refs built deterministically from the panel's own reviewer list and revision — never a Firestore collection query), re-runs the pure aggregation engine against exactly what was just read, and requires `ready` before writing anything. The panel schema gains a `"finalized"` terminal status with no reopening path. Canonical `approved_with_conditions` conditions are a deterministic exact-string union of the winning group's own conditions (never semantically merged); `changes_requested`/`rejected` get a fixed system-generated comment, never a reviewer's private text. A new, timestamp-independent deterministic decision ID is reused across every secondary artifact: new panel-lifecycle history, the EXISTING human-review history collection (reused unmodified, so single- and multi-reviewer decisions surface through the same history UI), a new idempotent governance event, a new admin-audit action, and the EXISTING `teamRuns` projection sync (also reused unmodified). Finalization is fully idempotent — a retry against an already-finalized panel returns the original outcome unchanged, and fails closed rather than guessing if canonical state and the panel ever disagree. An internal repair service backfills missing secondary artifacts for an already-finalized panel. Full detail: `docs/governance-decision-receipts-design.md` §33.

**Multi-Reviewer Owner Override and Panel/Vote UI (Part F), now LIVE — multi-reviewer panels are now a complete, backend-and-UI feature.** An owner (never an admin — deliberately narrower than ordinary finalization's own `owner`/`admin` gate) may explicitly override an open panel (waiting, deadlocked, OR ready) via `POST /api/teams/adaptive-runs/{runId}/review-panel/override`, immediately finalizing the canonical review with a status/conditions the owner chooses and a REQUIRED justification — never reading, mutating, or aggregating votes as a precondition or input. Override is a genuinely SEPARATE finalization path from aggregation finalization: its own decision-ID hash (which, unlike the aggregation path, includes the request's own content, since there is no separate aggregation outcome to derive idempotency from), its own `decidedVia: "multi_reviewer_owner_override"`/`finalizedVia: "owner_override"` provenance, its own panel-history/governance-event/admin-audit actions, and its own repair service — never a variant of Part E's own finalization transaction. One disclosed, additive fix was required in Part E's own finalization transaction: its idempotency check previously misclassified an override-finalized panel as `inconsistent_finalization_state` (fail-closed and safe, but semantically wrong) rather than recognizing it as "already decided via a different path" — fixed with a new `panel_already_finalized` reason, purely additive (every pre-Part-F panel is unaffected). `GET .../review-panel` is extended (additively) into a rich per-run read model: live per-reviewer vote status (visible to every reviewer, not just its author — comment/conditions text remains self-only and is never returned by this endpoint at all), a freshly-recomputed `aggregationState`, and four server-derived capability flags (`canManagePanel`/`canVote`/`canFinalize`/`canOverride`) that the new UI gates every mutating control on — the client never independently re-derives a role/eligibility check. Five new UI pieces (`components/teamGovernance/AdaptiveMultiReviewerPanelSection.tsx` and its four supporting components) render panel management, reviewer selection, vote submission, quorum/finalization, and the owner-override form, reusing the existing generic decision-option/conditions-editor components unmodified; `AdaptiveReviewDetail.tsx` hides the existing (unchanged) single-reviewer assignment/decision UI exactly while a panel is open or finalized, restoring it automatically once cancelled or absent. Every open panel now has a supported forward path — no panel can be permanently stranded. Full detail: `docs/governance-decision-receipts-design.md` §34.

**Multi-Reviewer Production-Readiness Hardening, Seeded End-to-End Validation, and Release Controls (Step 5), now LIVE — feature is release-ready, disabled by default, with one disclosed cross-cutting limitation.** A new global env-var kill-switch, `MULTI_REVIEWER_GOVERNANCE_ENABLED` (`lib/env.ts`, `=== "true"` pattern, `false` unless explicitly set), is checked ONLY at panel creation/reconfiguration (`PUT .../review-panel`) — never at vote/finalize/cancel/override, which are drain operations that must always remain reachable so an already-open panel can never be permanently stranded by a rollback. This required splitting Part F's single `canManagePanel` flag into two independently-gated flags: `canReconfigurePanel` (requires BOTH the team's own `adaptiveMultiReviewerSettings.enabled` opt-in AND this new global guard) and `canCancelPanel` (requires neither — cancel is also a drain operation). The UI (`AdaptiveMultiReviewerPanelSection.tsx`) reflects this split: when the global guard is off, "Reconfigure reviewers" disappears with an explanatory message while Finalize/Cancel/Override remain fully available — verified live by toggling the env var against a real running dev server and confirming the round trip in-browser (button disappears, reappears on re-enable, no data loss). #### Classifier silent-fallback-to-generic root cause (2026-08-05), FIXED

**Root cause, confirmed by directly invoking the real classifier against the live Gemini API (not inferred from code reading):** `classifyQuery()` (`lib/adaptiveSchema/classifier.ts`) called `gemini-2.5-flash` with `maxOutputTokens: 300`. This SDK/model combination shares its internal "thinking" token budget with `maxOutputTokens` — the connector never set `thinkingConfig`, so thinking silently consumed nearly the entire 300-token budget on every call (`finishReason: "MAX_TOKENS"`, ~12 visible completion tokens), truncating the JSON response to a few characters. `JSON.parse` then failed and `classifyQuery()` fell through to its `genericFallback("malformed_json")` path — for EVERY query, regardless of actual type, not just the two categories (Comparison, Risk Analysis) initially reported. This is why adaptive runs across the board rendered through the "restored" List/Compare/Synthesis/Trust-Summary/Verification-Gate shell (`AdaptivePanelResponse.tsx`'s fallback path for the pre-Milestone-2 schemas, including `generic`) instead of any Milestone-2 dedicated renderer: `generic` was nearly always the ACTUAL classification received, not a downstream renderer-selection bug — every Milestone-2 schema's dedicated renderer wiring (`comparison_matrix`→`ComparisonMatrixView`, `checklist_taxonomy`→`ChecklistTaxonomyView`, etc., all in `AdaptivePanelResponse.tsx`) was already correct and reachable, just never actually reached.

**Fix, in two parts, both verified against the live API:**
1. `lib/connectors/gemini.ts` gained a `thinkingBudget` connector option (`ConnectorCallOptions`, `lib/connectors/types.ts`) passed through to `generationConfig.thinkingConfig.thinkingBudget` (untyped in this SDK version's `.d.ts` but accepted by the REST API — cast, not a real type gap). `classifyQuery()` now passes `thinkingBudget: 0` (classification is short structured JSON with no benefit from reasoning) and raised `CLASSIFIER_MAX_OUTPUT_TOKENS` from 300 to 1024 as defense in depth. A related pre-existing bug was fixed alongside it: the connector's own truncation detector compared `finishReason` against the string `"MAX_OUTPUT_TOKENS"`, but the API actually returns `"MAX_TOKENS"` — so `wasTruncated` was always `false` even on a genuinely truncated response, masking the underlying failure from the connector's own logging. Both are now checked.
2. `ClassificationSchema` (`lib/adaptiveSchema/classifier.ts`) used strict Zod enums for every field — observed live: the model occasionally returns a `freshness`-shaped value (e.g. `"recent"`) for the similarly-named `timeSensitivity` field (`low`/`medium`/`high`), which used to fail the ENTIRE classification via `safeParse` and discard an otherwise-correct `queryType`. The 7 cross-cutting metadata enums (`timeSensitivity`/`userIntent`/`riskLevel`/`evidenceRequirement`/`freshness`/`inputType`/`verificationMethod` — never used to select a renderer) now use `.catch(default)`, degrading just that one field to a safe default instead of the whole response; `queryType`/`answerShape` remain strictly validated since they ARE render-critical.

**Comparison/Risk Analysis renderer completeness, addressed alongside the root-cause fix (query-routing redesign policy: no new schema/category without a genuine capability gap — neither was added):**
- `comparison_matrix` already had a dedicated renderer (`ComparisonMatrixView.tsx`) but only showed the (subject, attribute) grid — no answer-first conclusion, cross-cutting trade-offs, per-use-case recommendations, or stated uncertainties. `comparisonMatrixFields` (`schemaRegistry.ts`) gained 4 new flat fields (`directConclusion`, `tradeoffs`, `bestUseRecommendations`, `uncertainties`); `comparisonAlignment.ts`'s `buildComparisonMatrixResult()` aggregates them (modal/longest for the single conclusion, near-duplicate merge-and-rank — the same `dedupeTextList`/`mergeAndRankTextItems` machinery `checklistAlignment.ts`'s Notes list already uses — for the three lists); `ComparisonMatrixView.tsx` renders them as new sections above/below the grid.

Rather than adding one, `ChecklistItem`/`AggregatedChecklistItem` (`types.ts`) gained 7 OPTIONAL risk-register fields (`severity`/`likelihood`/`impact`/`evidence`/`mitigation`/`monitoringSignal`/`residualRisk`) that the model populates only when an item genuinely is a risk (prompt guidance in `promptBuilder.ts`'s `CHECKLIST_ITEM_INTERFACE`/checklist-specific instruction paragraph); left entirely unset for an ordinary checklist. `isRiskShapedChecklistResult()` (`types.ts`, deliberately NOT in `checklistAlignment.ts` — that module is `"server-only"` and this needs to be callable from the client renderer) detects a risk-shaped result from the DATA the panel actually produced (≥50% of items carry a risk field), never from the question's own wording. `AdaptivePanelResponse.tsx`'s `checklist_taxonomy_view` branch now picks a new `RiskAnalysisView.tsx` (executive risk conclusion, risk register grouped by category with severity/likelihood badges + impact/evidence/mitigation/monitoringSignal/residualRisk detail + per-risk consensus/disagreement coverage badge, unknowns from the existing `notes` field) over the plain `ChecklistTaxonomyView.tsx` when risk-shaped, preserving the plain view unchanged for ordinary checklists. ## Synthesis

### Request flow

`POST /api/synthesize-panel` — called automatically by the frontend after a panel run completes.

Synthesis is generated by **GPT-5.1** (not the panel models). It uses a compact cluster-based input rather than raw model outputs for efficiency. Results are cached in Firestore at `runs/{runId}.synthesizedStructuredReport`; subsequent requests for the same `runId` return the cached version.

Server-side timeout: 300 seconds.

### Output schema (`lib/synthesis/structuredSchema.ts`)

```ts
StructuredSynthesis {
  executiveSummary: string
  keyFindings: Array<{
    claim: string
    support: "strong" | "moderate" | "weak" | "contested"
    positionsByModel: Record<ModelId, string>   // each model's stance
    evidence: string[]
  }>
  disagreements: Array<{
    topic: string
    positionsByModel: Record<ModelId, string>
    significance: "high" | "medium" | "low"
  }>
  biasAndBlindSpots: Array<{
    description: string
    affectedModels: ModelId[]
    evidence: string
  }>
  openQuestions: string[]
  methodology: string
}
```

### Synthesis consensus scoring (`lib/verification/consensusScoring.ts`)

A separate algorithm from claim verification scoring. It works by:

1. Extracting anchor tokens from each key finding
2. Checking each model's `positionsByModel` text for negation within a detection window
3. Computing a support ratio per finding
4. Applying penalties:
   - −10 if ≥2 disagreements present
   - −10 if ≥1 bias/blind spot identified
   - −5 × weak finding count (capped at −25)
   - −10 if fewer than 4 healthy models contributed

## Claim Verification

### Request flow

`POST /api/verify-claim` → `lib/verification/runClaimVerificationPanel.ts`

Uses the same `CONNECTOR_MAP` as the panel but with a `systemPromptOverride`. Gemini receives `maxOutputTokens: 8192` for this mode.

### Verdict schema

Each model returns JSON matching:

```ts
{
  verdict: "accurate" | "partially_accurate" | "inaccurate" | "unverifiable"
  confidence: "high" | "medium" | "low"
  summary: string
  correctParts: string[]
  incorrectParts: string[]
  unverifiableParts: string[]
  reasoning: string
}
```

### Claim verification consensus scoring

Formula (defined in `lib/verification/consensusScoring.ts`):

```
score = 40
      + 45 × supportRatio
      + 20 × healthRatio
      − disagreementPenalty
      + verdictBoost
      − min(20, lowEvidenceClaims × 5)
```

Clipped to [0, 100].

- `supportRatio` = fraction of healthy models agreeing with dominant verdict
- `healthRatio` = fraction of models that returned a usable result
- `disagreementPenalty` = increases when models split across opposing verdicts
- `verdictBoost` = bonus when all models return identical verdicts
- `lowEvidenceClaims` = models that returned `"unverifiable"` on key points

### Audit bundle (`lib/verification/auditBundle.ts`)

Each verification stores an `AuditBundle`:

```ts
{
  version: number
  kind: "claim"
  claimCharCount: number
  modelCount: number
  verdict: string          // dominant verdict
  consensusScore: number
  perModel: Array<{
    modelId: ModelId
    verdict: string
    confidence: string
    status: ConnectorStatus
  }>
}
```

## Video Verification

### Request flow

`POST /api/verify-video` — 16-step pipeline:

1. Auth (session cookie → Bearer fallback)
2. Rate limit check
3. Plan check (video verification available on Lite and Full plans only)
4. Video quota check (`videoVerificationsThisMonth` in `users/{uid}`)
5. Request validation (max 50 MB, max 60 seconds)
6. Client-side frame extraction (browser API; frames sent as base64 JPEG)
7. Frame count selection: 4 frames for <3s video, 10 for normal, 12 for ≥55s (hard cap: 15)
8. Metadata heuristics analysis (`lib/video/videoPure.ts`)
9. Prompt construction
10. 3 vision model calls in parallel (GPT-4o, Claude, Gemini)
11. All vision calls use base64 inline images — no external URL hosting required
12. Majority verdict calculation
13. Consensus score computation
14. Firestore save to `videoVerifications` collection
15. Governance policy evaluation (Full plan)
16. Video usage counter increment

All three use 60-second timeouts and 8192 max output tokens.

### Video verdicts

```
"authentic_captured"    — appears to be genuine captured footage
"authentic_produced"    — professionally produced but not AI-generated
"likely_manipulated"    — signs of AI generation or editing
"inconclusive"          — insufficient signal to determine
"insufficient"          — too few usable frames or model failures
```

### Metadata heuristics

`analyzeMetadata()` in `lib/video/videoPure.ts` checks:

- Creation date (absent or suspiciously recent)
- Encoding software field — scanned for known AI tool signatures
- Aspect ratio (unusual ratios common in AI-generated video)
- Frame rate
- Audio presence / bitrate proxy

**Detected AI encoding markers:** runway, pika, sora, kling, synthesia, heygen, d-id, stable video, luma, minimax, hailuo

### Video consensus score

- Base: `dominantFraction × 100`
- Penalties: −10 for suspicious metadata, −15 for <3 usable models, −5 for >2 client warnings

### Multi-Reviewer Governance (adaptive runs, team plan)

A separate, panel-based review workflow layered on top of the adaptive schema system's `governanceRecord.humanReview`, distinct from the single-reviewer policy engine above. Lives at `runs/{runId}/humanReviewPanel/current` (one active panel per run) plus `runs/{runId}/humanReviewVotes/{revision}:{reviewerUid}` and `runs/{runId}/humanReviewPanelHistory/{revision}:{event}`. Panel lifecycle: create (`PUT`) → reviewers vote (`POST .../votes`) → aggregation reaches `waiting` / `deadlocked` / `ready` → finalize (`POST .../finalize`, majority aggregation) or owner override (`POST .../override`, breaks a deadlock) → cancel (`DELETE`) is available at any open-panel state as a drain operation. Route: `app/api/teams/adaptive-runs/[runId]/review-panel/`.

**Two-gate release model** — both required for any NEW panel activity (create/reconfigure): the global `MULTI_REVIEWER_GOVERNANCE_ENABLED` env var (`lib/env.ts`, defaults false, unset in production as of 2026-08-04 — see Authentication § above) AND the team's own Firestore opt-in (`team.adaptiveMultiReviewerSettings.enabled`). Cancelling an already-open panel and an owner's override are deliberately gated on **neither** — both are drain/escape-hatch operations that must stay available even after the feature is disabled team-wide or globally, so a panel can never become stranded by a rollback.

**Capability flags are entirely server-derived**, never re-derived client-side from the env flag or team settings: `GET .../review-panel` computes `canReconfigurePanel` / `canCancelPanel` / `canVote` / `canFinalize` / `canOverride` (existing-panel case) and `canCreatePanel` (no-panel case, added 2026-08-05 — see below) directly from `isTeamAdmin(role)`, the reviewability of the governance record, and the two-gate check; `components/teamGovernance/AdaptiveMultiReviewerPanelSection.tsx` only ever renders a control when the matching flag is true.

**`canCreatePanel` fix (2026-08-05):** the "Create a multi-reviewer panel" button used to render unconditionally whenever no panel existed, regardless of either gate — the server already rejected the resulting `PUT` with `403 multi_reviewer_disabled`, so this was a UX gap, not a security gap. `GET .../review-panel`'s panel-absent branch now returns `canCreatePanel` (mirrors `PUT`'s own creation gate exactly), and the client hides the button unless the server confirms creation is actually possible.

**Stale-`runId`-on-navigation fix (2026-08-04):** `AdaptiveMultiReviewerPanelSection` is never remounted by a client-side navigation between two runs under `/team/reviews/[runId]` — only its `runId` prop changes — so a slow, still-in-flight fetch for the PREVIOUS run could resolve after the new run's fetch and silently overwrite the panel state with the wrong run's data. Fixed with an `AbortController` per load, mirroring the pattern already established in `TeamReviewQueue.tsx`.

**Seed/test harness:** `scripts/seed-adaptive-multi-reviewer-e2e.ts` / `scripts/cleanup-adaptive-multi-reviewer-e2e.ts` — six deterministic scenarios (A–F) under the `gov-e2e-seed-` namespace, safe to run against production since this repo has no separate dev/staging Firebase project (`ALLOW_NON_PROD_GOVERNANCE_SEED=true` + `--confirm-project=convergepanel` both required). Cleanup defaults to dry-run; every candidate path is namespace-checked independently before any delete.

### Workspace Approval Workflow (Phase 9) — dark, Production-canary-proven, internal use only

A **separate, newer** governance system layered on the same `governanceRecord.humanReview` shape, scoped to the new Workspace model (`app/api/workspaces/[workspaceId]/...`) rather than the legacy `teams`/`teamRuns` collections the Multi-Reviewer Governance section above uses — do not conflate the two; they have independent env-var gates, independent admission resolvers, and never share code paths. Covers: single-reviewer assignment/decision/resubmit, multi-reviewer panel (create/reconfigure/vote/finalize/cancel), and Owner Override.

**Two independent, additive gates**, both required: Team Workspace access (`resolveTeamWorkspacesMode()`, `TEAM_WORKSPACES_ENABLED`/`TEAM_WORKSPACES_CANARY_UIDS`) and Approval Workflow admission (`resolveApprovalWorkflowAdmission()`, `APPROVAL_WORKFLOW_ENABLED`/`APPROVAL_WORKFLOW_CANARY_UIDS`, `lib/workspaces/approvalWorkflowRollout.ts`). **Current Production state: both gates dark** (`APPROVAL_WORKFLOW_ENABLED=false`/unset, canary UID list empty/absent). The canary validated the **governance state machine**; it is not itself authorization for external, broad, or global rollout — see the runbook below for the exact rollout-tier decision and outstanding prerequisites (Team invite-canary admission, panel-mutation audit coverage, UI post-mutation reconciliation).

## Workspaces (Personal) — LIVE IN PRODUCTION as of 2026-08-14

Full architecture, phase-by-phase design rationale, flag matrices, and rollout evidence: **[`docs/workspaces/architecture.md`](./workspaces/architecture.md)**.

Every user gets exactly one deterministic Personal Workspace (`workspaces/personal-{uid}`, `lib/workspaces/personalWorkspaceId.ts`) — id construction is never reimplemented inline anywhere in the codebase. Provisioning is idempotent (Firestore `.create()` only, no transaction needed) via the single canonical `ensurePersonalWorkspace()` (`lib/workspaces/ensurePersonalWorkspace.ts`), reused verbatim by every call site:

- **Self-service** (`POST /api/user/workspace`, `app/api/user/workspace/route.ts`) — called from both `/login` and `/signup` client code, **awaited before the app redirect proceeds**. This is what makes provisioning "steady-state": a user can never enter the app without a Workspace, and a Workspace that goes missing for an existing user self-heals on their next login. Gated by `PERSONAL_WORKSPACE_PROVISIONING_ENABLED` (`lib/env.ts`), independent of the two flags below.
- **Bulk backfill** (one-time, historical) — `scripts/workspaces/provision-existing-personal-workspaces.ts`, used once to provision the pre-existing user population before Workspace-aware writes went live. Not part of any runtime code path.

**Workspace-aware writes** — newly created Personal (non-team) **adaptive** research runs are persisted with an optional `workspaceId` pointing at the owner's Workspace (`lib/workspaces/personalRunWorkspaceBinding.ts`, wired into `POST /api/run-panel`). Deep Research (non-adaptive), Claim Verification, Video Verification, and all team runs are entirely unaffected — `workspaceId` is simply absent on those documents; no historical run has ever been mutated, and none will be until a separate, later backfill phase. A missing/invalid Workspace fails the request closed (`workspace_prerequisite_failed` / `workspace_configuration_invalid`) **before** any model call, usage increment, or run creation — the binding check never provisions a Workspace as a side effect.

Two independent flags gate this, both required, checked in this order in `resolvePersonalRunWorkspaceBinding()` (team exclusion is checked before the flag-configuration invariant — this ordering was itself a fixed defect, see architecture doc):

| Flag | Purpose |
|------|---------|
| `WORKSPACES_ENABLED` | Authorization/read prerequisite — do reads honor a persisted `workspaceId` at all |
| `PERSONAL_RUN_WORKSPACE_WRITES_ENABLED` | Write rollout switch — global, currently `true` in production |
| `PERSONAL_RUN_WORKSPACE_WRITE_CANARY_UIDS` | Optional comma-separated account-scoped allowlist that can enable writes for specific uids independent of the global flag (used for staged canaries; absent once a rollout goes global) |

**Production status:** Personal Workspace provisioning and Workspace-aware writes are fully live and global (`PERSONAL_WORKSPACE_PROVISIONING_ENABLED=true`, `WORKSPACES_ENABLED=true`, `PERSONAL_RUN_WORKSPACE_WRITES_ENABLED=true`, no canary allowlist). This was reached through four staged production releases — a single-account write canary, a lifecycle-provisioning release (new-signup + login-self-heal), a small multi-account write canary, and finally the global write enablement — each with its own read-only population reconciliation and rollback rehearsal, with zero rollbacks needed at any stage. **Not yet started:** backfilling `workspaceId` onto pre-existing runs, making any read path treat `workspaceId` as security-relevant, Workspace UI, or Projects — all deliberately separate future phases.

## Team Workspaces — canary-scoped, member management + Audit Log merged 2026-09-01

Shared/collaborative Workspaces, layered additively on top of the Personal Workspace foundation above — nothing about Personal Workspace behavior is affected. Full architecture, phase-by-phase design rationale, and the frozen role/capability model: **[`docs/workspaces/phase8-team-workspace-foundation.md`](./workspaces/phase8-team-workspace-foundation.md)** (foundation) and **[`docs/team-workspaces-architecture-audit.md`](./team-workspaces-architecture-audit.md)** (pre-Phase-8 data-model audit). This section only documents this doc's first real coverage of the subsystem plus what most recently merged — it is not a complete route/feature catalog; see the linked docs for that.

**Membership model.** A Team Workspace (`workspaces/{workspaceId}`, `type: "team"`) has a `workspaceMemberships/{computeMembershipId(workspaceId, uid)}` document per member — `active` or `removed` status, never hard-deleted. Five roles, each a frozen, flat capability set (`lib/workspaces/capabilities.ts`): **Owner** (all capabilities, exactly one per Workspace, verified via `isCanonicalTeamOwnerMembership()` against `workspace.ownerUserId` — never a bare `role === "owner"` string check), **Admin**, **Member**, **Reviewer**, **Viewer**. Every mutation authorizes through the single canonical `resolveWorkspaceAccess()` (read paths) or `authorizeTeamWorkspaceMutationInTransaction()` (transaction-scoped writes) — no route re-derives membership/role logic inline. Rollout gate: `TEAM_WORKSPACES_ENABLED` / `TEAM_WORKSPACES_CANARY_UIDS` / `TEAM_WORKSPACES_CANARY_WORKSPACE_IDS` (see Environment Variables below) — **canary-scoped in Production as of 2026-09-01**, not enabled for the full user base.

**Active member removal (Phase 12A).** Owner may remove Admin/Member/Reviewer/Viewer; Admin may remove Member/Reviewer/Viewer only (never another Admin); the canonical Owner can never be removed through ordinary member management — only through the pre-existing `transferTeamWorkspaceOwnership()` transaction. Self-removal is always rejected. Soft-removal only (`status: "active" → "removed"`, `removedAt`/`removedByUserId` server-derived) — the membership document, role, and invitation provenance are retained forever. `POST /api/workspaces/{workspaceId}/members/{uid}/remove`, empty request body (every fact is server-derived from the session + URL path).

**Workspace Audit Log (Phase TEAM-GOV-I1).** A new Workspace-native governance surface — `GET /api/workspaces/{workspaceId}/audit-events` + `/workspace/team/{workspaceId}/audit` — gated on the `audit.read` capability (Owner/Admin only). Reads a new `workspaceMembershipEvents` collection (v1 scope: `workspace_member_removed` only). Deliberately independent of the legacy `/api/governance/audit` dashboard covered under Governance below — that surface's authorization model (admin-email / reviewer-assigner relationships, billing-plan gate, viewer's-own-actions-only filtering) has no Workspace-native concept and was judged the wrong foundation to extend. Bounded (default page size 20, max 50), deterministic `at DESC` + document-ID-tiebreak ordering with an opaque cursor, presentation DTO is an explicit allow-list (no raw UID/workspace ID ever reaches the client — actor/target render as resolved display names, falling back to "Unknown user"/"Unknown member").

**Atomicity.** The `workspace_member_removed` event is written via `tx.set()` **inside the same Firestore transaction** as the membership removal itself — both commit or neither does (`REMOVAL COMMITTED IFF AUDIT EVENT COMMITTED`). This was a corrective fix during review: the first implementation wrote the event as a separate, best-effort, post-commit call (matching this codebase's usual event-writer pattern — see `admin_audit_logs`/`writeAuditEvent()` and `projectEvents`/`writeProjectEvent()` below), which would have allowed a real removal to leave zero audit trail on a transient write failure. That ordinary best-effort pattern remains correct and unchanged for every other event writer in this codebase; it was judged insufficient specifically for this authorization-changing, governance-relevant operation.

**Firestore index.** `workspaceMembershipEvents`: `workspaceId ASC, at DESC` (`firestore.indexes.json`) — deployed to the Production Firestore project (`convergepanel`) via `firebase deploy --only firestore:indexes` on 2026-09-01, separately from the Vercel application deploy (Vercel does not deploy Firestore indexes as part of a Next.js build — this is a standing operational reminder for any future collection that needs a composite index).

**Merge history:** implemented as two stacked PRs (#116 member removal, #117 Audit Log) reviewed independently, then combined and merged to `main` as a single atomic PR (#117 retargeted from `main`, PR #116 absorbed/marked merged automatically once its commits became reachable) to avoid a window where removal existed without its audit trail. Merging to `main` was confirmed to trigger an automatic Vercel Production deployment.

## pSEO Architecture

All 292 use-case pages are defined as a single `PAGES: PSEOPage[]` array in `lib/pseo/pages.ts`. There is no CMS. The dynamic route `app/use-cases/[slug]/page.tsx` renders every page. The hub at `app/use-cases/page.tsx` has a separate `HUB_GROUPS` array that controls which pages appear and how they are grouped in the hub UI.

`app/sitemap.ts` auto-generates from `PAGES` using the `publishedAt` field as `lastModified`. The same `publishedAt` value populates `dateModified` in JSON-LD structured data — it is the only freshness signal available and should be updated on any meaningful content change.

|-------|------|-------|
| `slug` | string | URL path segment; must be unique |
| `title` | string | `<title>` tag |
| `h1` | string | Page heading |
| `metaDescription` | string | `<meta name="description">` |
| `audience` / `audienceDetail` | string | Used in structured data |
| `problem` / `solution` | string | Intro section copy |
| `workflow` | string[] | Numbered steps |
| `useCases` | string[] | Bullet list |
| `cta` | string | Call-to-action button label |
| `category` | string | Used for hub grouping |

| `relatedLinks` | `{ label, href }[]` | Internal links; keep under ~9 |

### IndexNow

Bing (and Yandex/Seznam/Naver via the shared protocol) only crawl on their own schedule unless pinged. `scripts/submit-indexnow.mjs` POSTs URLs to `https://api.indexnow.org/indexnow`; the key file at `public/97ce1cedaadd35047076e3cc65939bd8.txt` must be live in production for the endpoint to verify the submission (it fetches the file from `convergepanel.com` before accepting).

Run `npm run seo:indexnow` after any PSEO edit session — it diffs `PAGES` against `scripts/.indexnow-state.json` (committed) and submits only slugs whose `publishedAt` changed since the last successful run. Use `npm run seo:indexnow -- --all` to resubmit every URL in the sitemap, or pass explicit slugs to submit only those. State is only persisted on a successful (2xx) response, so a failed submission (e.g. key not yet deployed) doesn't get silently marked as done. Reusable submission logic for future runtime use (e.g. firing from a publish API route) lives in `lib/pseo/indexnow.ts`.

## Theme

The application uses a light theme globally (`body { background: #F6F6F3 }`, Hanken Grotesk font), switched from an earlier dark theme in July 2026. All UI must use the `cp-*` design tokens defined in `tailwind.config.ts` and `globals.css` (`cp-bg`, `cp-surface`, `cp-raised`, `cp-text`, `cp-muted`, `cp-accent`/`cp-primary`, `cp-border`, etc.) — no `dark:` Tailwind variants (the app has no dark-mode toggle). See `CLAUDE.md` for the full token reference and readability conventions (e.g. `-600`/`-700` shades for colored text on light backgrounds, not `-300`/`-400`).

Note: `app/page.tsx` (the main Research/Verify Claim/Verify Video dashboard) predates the token system and uses hardcoded Tailwind classes (`bg-white`, `text-slate-900`, etc.) instead of `cp-*` tokens — it happens to already match the light theme but won't pick up future token changes automatically.
