## 1. Owner rulings

| # | Ruling |
|---|---|
| R1 | The controlled beta excludes the **additional, optional API synthesis feature**. This does **not** automatically forbid the existing research-pipeline Gemini operations (classification, bias detection, coverage audit, narrative generation, and others). Each such operation must be **inventoried**. Required pipeline behaviour must be distinguished from optional synthesis. **No additional provider calls are authorized.** The documentation must not claim that no synthesis or narrative generation occurs if the pipeline performs it. Auxiliary processing of customer content must be **disclosed** and must pass the D6 provider-processing controls. The shared web pipeline must not be silently modified. |
| R2 | **Full raw model responses are excluded from the controlled beta.** Only approved structured engine outputs may be returned, through documented, provenance-preserving schemas. Limited attributed excerpts are allowed only when permitted by the contract, the data-processing terms, sanitization, retention and deletion, and the customer's authorization and scope. Excerpts must not be used to reconstruct substantially complete responses. No evidence, finding or attribution may be fabricated. |
| R3 | A **unanimous panel judging a claim inaccurate must not be described to API customers as model disagreement.** The per-model verdict distribution must be preserved. Agreement that a claim is inaccurate, genuine disagreement, and independent factual verification (which consensus does not establish) must be distinguished. The current `computeClaimVerdict` may return `disputed` for a unanimous "inaccurate" panel; this is a **defect to be documented**. Production web semantics are **not** changed in this PR; the web impact needs a **separate assessment**. The API needs a truthful, contract-compatible representation **without inventing a new verdict or re-scoring**; if none is safe, that output is **not advertised as fully supported**. |
| R4 | Consensus must have a **defined, supported meaning per schema**. It describes model agreement only where the computation supports it. It is never a substitute for factual accuracy, verification, evidence reliability or an unsupported confidence. If it is unavailable, the approved `unavailable` section state is returned with a precise reason. No manufactured scores and no unrelated measures. |

## 2. Requirements restated for the corrections

- **m3 (mandatory).** An authenticated, currently authorized caller replaying the original accepted request (same `Idempotency-Key`, same canonical request) receives the original accepted job and response, even if dynamic conditions changed. Order: authenticate and establish current authorization (revoked credentials never regain access through a replay) → transport safety and bounded parsing and canonicalization → locate the record within its authorized organization, application and mode → a committed match returns the original response before any new-job-only check, with no new job, reservation, dispatch or charge → a different canonical request is the documented 409 → a deleted original applies the approved deletion and replay contract → an in-flight record is answered consistently with the existing documents. Rate limiting may throttle replays but must not cause duplicate work or billing.

## 4. Open owner decisions created by this round

1. **Body cap and non-NFC input (B): OWNER DECISION REQUIRED.** 512 KiB does not admit every legal request: one whose text is both decomposed and fully `\u`-escaped can reach 1,010,418 bytes. Options (a) also bound raw code points, (b) reject non-NFC input, (c) raise the cap, (d) keep 512 KiB and document the boundary; evidence in `error-catalog.md` §4.3.1. Until decided, the 524,288-byte cap and step 1 (413) apply.
2. **Deleted record and a different request (m3, `jobs-and-idempotency.md` §5A.3 row T18).** The deleted marker is content-free (it keeps no request hash), so a different request under that key also gets 410. Engineering decision within the approved deletion contract; owner confirmation requested.
3. **D6 acknowledgement on replay (m3, §5A.1).** Classified as a new-job-only condition: a withdrawn acknowledgement does not block a replay, which sends nothing to any provider. Owner confirmation requested.
4. **Visible-content edge cases (m4).** Private-use and unassigned code points and U+2800 BRAILLE PATTERN BLANK count as visible. Owner may narrow them.
5. **Metadata aggregate (4,000 code points)** is a placeholder for owner sizing.
6. **m6, `js-yaml`: OWNER DECISION REQUIRED.** The docs specs still import `js-yaml`, which `package.json` does not declare (it resolves through `eslint@8`). This round was not allowed to change `package.json` or to write a YAML parser. Options: (a) declare `js-yaml@4.1.1` as a devDependency (the lockfile already resolves 4.1.1; needs approval for the `package.json` and lockfile change); (b) a vendored loader for the YAML subset `openapi.yaml` uses; (c) commit a generated JSON rendering of `openapi.yaml` plus a check that the two are equivalent.
7. **Rate-limit layering (m2).** The pre-authentication flood limit per source address (600/min, all routes) equals the per-key read limit (600/min), so a single client polling at its full key limit from one address is throttled by the address limit first, and several keys behind one address share 600/min. The failed-authentication lockout (30/min per address, then every request from the address gets 429) lets one misconfigured or hostile client behind a shared NAT or proxy deny service to every other customer behind the same address. The numbers and layering are unchanged in this round; the owner decides the relation between the two limits and whether the lockout should be narrower (for example only requests that present a key prefix that failed).
8. **Concurrency counter (m3 model caveat).** In the design the concurrency counter lives in the Redis-class store outside the Firestore snapshot, so concurrent creates under different keys can over-admit unless the implementation uses an atomic check-and-increment released on abort (`jobs-and-idempotency.md` §5A, reference-model note). Owner decides between the atomic design and a documented bounded over-admission.
9. **`cancel` on a deleted verification** returns 409 `not_cancelable` (`error-catalog.md` §3.1): `openapi.yaml` defines no 410 for `cancel`, and a deleted verification is always terminal. Engineering reading of the approved documents; owner confirmation requested.
