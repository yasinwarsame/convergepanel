# Adaptive Research Results and Export — Product, Privacy, Permissions, and Architecture Design

**Date:** 2026-08-05
**Scope:** design only, per explicit instruction. Existing code, schemas, permissions, governance records, UI components, and legacy export logic were read and audited; **no export routes, components, services, storage, templates, permissions, or database changes were made.**
**Precondition — resolved 2026-08-05 (see §12.1):** the classifier fix (PR #5) and the production-flag enablement (PR #6, docs) are merged and verified live. **No structured canary was run** — both flags were enabled at 100% immediately (not a limited-team rollout), verified only by two manual live spot-checks (the originally reported Comparison and Risk Analysis queries). This differs from this project's own established canary convention (`docs/operations/multi-reviewer-governance-runbook.md` §11: limited team + one business week of monitoring before wider rollout). Given the flags are already fully live and reverting is a bigger disruption than monitoring forward, the resolution is to treat the next real business week of production traffic as the de facto monitoring window (via existing `admin_audit_logs`/governance telemetry, no new tooling needed) rather than re-run a formal canary retroactively. Phase 1 implementation may proceed in parallel with that monitoring window — it does not block on it.
**Method:** every finding below is grounded in a fresh read of the actual code (`lib/adaptiveSchema/*.ts`, `lib/governance/*.ts`, `lib/plans.ts`, `lib/verification/generateMemo.ts`/`shareText.ts`, `app/api/teams/audit-export/route.ts`), not assumed from the brief's own framing.

## 1. Executive summary

The brief's 8 non-negotiable constraints and 7-phase sequence are sound and I'd approve them as stated. This document grounds them in what actually exists in this codebase today, and surfaces one finding that changes how Phase 3 must be built:

**There is no export system today, and no "legacy export contract" in the sense of a competing data contract to migrate away from — there is only `MemoInput`/`generateMemo.ts`, a flat, unversioned, plain-text memo generator with zero governance-awareness, built before the adaptive schema system existed.** `app/api/teams/audit-export/route.ts` is the only real export route in the codebase, and it explicitly excludes adaptive runs today (its own comment: *"a real adaptive export contract... is a genuine design decision deferred to a future step"* — this document is that step).

**The harder finding: `PersistedAdaptiveOutputV1` and `GovernanceRecordV1` are not versioned in the sense Constraint #1 needs.** Both are embedded, single-value fields on `runs/{runId}` (`adaptiveOutput`, `governanceRecord`) that are overwritten in place on re-review, retry, or repair — there is no history, no "supersedes" pointer, no immutable snapshot store. **Constraint #1 ("export only immutable snapshots... a versioned snapshot of the research run, not from live mutable records") cannot be satisfied by exporting from these fields directly, no matter how the export route is written**, because the source of truth itself is mutable. The correct fix (detailed in §6) is cheap and doesn't touch existing storage: an export is generated by reading the live records **once, at generation time**, and freezing that read into its own immutable, versioned artifact (`AdaptiveResearchExportV1`) with its own storage location and its own manifest. The *export* is the snapshot; the *source records* stay exactly as they are today. This also directly enables the new "Superseded" status (§5.1) — comparing export generation timestamps against the live record's `humanReview.reviewedAt`/`updatedAt`, not a new source-of-truth versioning system.

**Also found:** `lib/plans.ts` already has `advancedExportEnabled: boolean` (false on Free, true on Lite/Full) and `teamGovernanceAccess?: boolean` (Full only), and the Full plan's own marketing copy already promises *"Unlimited saved panels & advanced exports (Markdown / PDF / copy-ready) - Available in next release"* — this feature has an existing billing commitment. The new permission model (Constraint #4) must layer **on top of** plan-tier gating, not replace it: plan tier decides *whether export exists at all* for this user; the new `export_*` permissions decide *what* an eligible user may include.

Everything below is organized to match the brief's own phase numbering so it can be reviewed against it directly.

### 3.2 The dependency this creates on Phase 1

The brief is explicit that "the primary screen should show the reviewed conclusion first." **That screen does not exist yet** — items 1, 2, and 7 above require a new component that reads `GovernanceRecordV1` and renders it *above* the existing schema-specific renderer, not a new export capability. This is not optional scaffolding for export; it's the same status model export needs (§5.1), just rendered in-app instead of in a file. Building it first (as the brief's phase order already implies) means the export's "unmistakable status" requirement (Constraint #2) reuses one status computation, not two.

**Recommendation:** Phase 1's deliverable should be a `ReportStatusBanner` component (name illustrative, not prescriptive) that both the in-app result view and the future export renderer consume — same status enum, same source data, computed once server-side and never re-derived client-side (matching the `canManagePanel`-style precedent).

**Superseded by `docs/adaptive-synthesis-report-design.md` (2026-08-05).** That document's §4.1 "top summary bar" is this Phase 1 deliverable, generalized across all 19 active schemas rather than built export-first — build it there, not as a separate export-only component. This export document's own Phases 3–7 should not begin implementation until that document's §5 category-specific report components ship; see its §8 for the reconciled sequence.

## 4. Report status model (Constraint #2)

### 4.1 Status derivation table

The brief lists 7 states; grounding them against `GovernanceRecordV1.humanReview.status` (`unreviewed | pending | approved | approved_with_conditions | changes_requested | rejected`) plus `decidedVia` surfaces **one state the brief didn't separate and two states that don't exist in the source data yet.**

**Correction found on review (2026-08-05):** `"pending"` is defined in the type and has documented semantics (`governanceRecordParser.ts`: *"a review has been started/assigned but has not yet reached a substantive human decision"*), but confirmed via code search — no write site anywhere sets `humanReview.status: "pending"`; `initializeAdaptiveGovernanceRecord()` always initializes to `"unreviewed"`, and reviewer assignment (Part E3) explicitly never touches `humanReview.status`. In practice, only 5 values ever occur. This document's derived label **"Unreviewed — pending"** below is this document's own UI label, not a reference to the raw `"pending"` enum value — renamed to **"Unreviewed — in queue"** to remove the collision, since a future reader could otherwise assume the label maps to that (currently unreachable) status value.

| Brief status | Derived from | Notes |
|---|---|---|
| Unreviewed — in queue | `humanReview.status === "unreviewed"` AND the run was actually routed toward review (`adaptiveTeamReviewProjectionStatus` ∈ `{"created", "already_exists"}`, i.e. `routeAdaptiveTeamReview()` returned `flagged`/`blocked`/`human_review_needed`/`all_runs`) | **Resolved 2026-08-05, see §12.2.** Confirmed by code read (`app/api/run-panel/route.ts`'s governance-initialization block): `GovernanceRecordV1` is initialized **unconditionally** for every adaptive run whose `adaptiveOutput` persisted — solo/Free/Lite runs get one too, with no team or reviewer ever assigned. Split into two labels so "Unreviewed" doesn't misrepresent runs that were never going to be reviewed. |
| Not reviewed — no review configured | `humanReview.status === "unreviewed"` AND `adaptiveTeamReviewProjectionStatus` ∈ `{"disabled", "not_eligible"}` (or absent — no team) | The common case for Free/Lite/solo Full-plan users. Must not read as an outstanding action item. |
| Reviewed and approved | `humanReview.status === "approved"` | — |
| Reviewed with conditions | `humanReview.status === "approved_with_conditions"` | Export must show `humanReview.conditions[]` verbatim per Constraint #2's "must be unmistakable" — never summarized. |
| Rejected | `humanReview.status === "rejected"` | — |
| Changes requested *(not in brief — resolved as its own status)* | `humanReview.status === "changes_requested"` | **Resolved 2026-08-05, see §12.3:** kept as its own 8th status, distinct from "Rejected." A rejection is terminal; `changes_requested` implies a resubmission path exists. Collapsing it into "Rejected" would misrepresent an in-progress state as final. |
| Owner override | `humanReview.decidedVia === "multi_reviewer_owner_override"` | Combine with the underlying `status` (e.g. "Owner override — Approved"), since override sets a real terminal status too. |
| **Incomplete** *(new — no source field yet)* | Recommend: `PersistedAdaptiveOutputV1` absent/`persistenceStatus !== "saved"` (mirrors the existing `"saved" \| "failed" \| "omitted_size_limit" \| "not_applicable"` field already returned by `persistAdaptiveOutput()`), OR the classification routed to `graceful_limitation`/`disabled`/`handoff` (no real report was ever produced), OR fewer than N models produced usable output. **No such computed flag exists today** — needs to be added in Phase 2/3, not invented ad hoc at export time. |
| **Superseded** *(new — no source field yet)* | Recommend: computed at export-list time by comparing this export's frozen `generatedAt`/`reportVersion` against the run's *current* `humanReview.updatedAt`/`adaptiveOutput.generatedAt` — if either moved on since this export was generated, the export is Superseded. **Does not require new mutable-record versioning** (see §1's central finding) — it's a comparison the export listing UI does at read time against two timestamps that already exist. |

### 4.2 "Raw model output must not present as approved conclusion"

Read literally from the brief (garbled in the source text but the intent is unambiguous, and it matches Constraint #3's exclusion of raw model responses from the default export). Concretely: the default export (§5.2) never includes `AdaptiveModelResult.data`/raw per-model text, and wherever the in-app UI or export shows a per-model raw response (List View, Compare View, an explicit "include raw" opt-in export), it must carry its own model attribution and never be laid out under the "Reviewed and approved" banner's visual scope — status banners apply to the *aggregated report*, never to a single model's raw output.

## 5. Phase 2 — Export policy and privacy design

### 5.1 Field-level exportability matrix

| Field / section | Default (least-privilege) export | Requires permission | Classification floor | Source |
|---|---|---|---|---|
| `decisionReceipt.conclusion` | ✅ Included | `export_final_report` | Internal | `AdaptiveDecisionReceipt` |
| Consensus findings | ✅ Included | `export_final_report` | Internal | schema-specific (e.g. comparison `consensus`/`majority` cells) |
| Material disagreements | ✅ Included | `export_final_report` | Internal | schema-specific (e.g. `split` cells, `changes_requested` conditions) |
| `decisionReceipt.uncertainties`/`limitations` | ✅ Included | `export_final_report` | Internal | `AdaptiveDecisionReceipt` |
| Approved sources/citations | ✅ Included | `export_sources` | Internal | `decisionReceipt.sources[]`, per-schema `sources` |
| Final governance status (§4) | ✅ Included | `export_final_report` | Internal | `GovernanceRecordV1.humanReview.status` |
| Raw per-model responses | ❌ Excluded by default | `export_raw_model_outputs` | Confidential | `AdaptiveModelResult.data` |
| Private reviewer comments | ❌ Excluded by default | `export_reviewer_identity` (comment text) — **never** exportable without it | Confidential | `humanReview.comment` |
| Internal notes / hidden conditions | ❌ Excluded by default | `export_governance_evidence` | Confidential | any field not in `decisionReceipt`/`humanReview.conditions` (the *public* conditions) |
| Model prompts | ❌ Excluded, always | *(no permission grants this — see below)* | Restricted | `promptBuilder.ts` output, never persisted per-run today anyway |
| System prompts | ❌ Excluded, always | *(no permission grants this)* | Restricted | `CLASSIFIER_SYSTEM_PROMPT` etc. — not run-specific data at all; exporting it would leak product IP, not run content |
| Security metadata (uid, session, IP, tokens) | ❌ Excluded, always | *(no permission grants this)* | Restricted | never appears in any export path |
| Internal identifiers (Firestore doc IDs, `panelRevision`, internal `decisionId` hashes) | ❌ Excluded by default | `export_governance_evidence` (for audit-oriented exports only, in the manifest, never in report body) | Confidential | `GovernanceRecordV1` internals |
| Reviewer identity (name/email) | ❌ Excluded by default (masked) | `export_reviewer_identity` | Confidential | reuse `maskEmail()` |

Two rows have **no grantable permission at all** — prompts and security metadata are not "sensitive fields," they're not run-content at all, and treating them as a same-tier permission risk as "raw model outputs" would wrongly imply they're legitimate power-user data. This is a stronger stance than Constraint #4's `export_sensitive_fields` alone would express, so I'm flagging it as an addition, not an assumption: recommend prompts/security metadata are **hard-excluded at the code level**, not gated behind a permission a super-admin could grant.

### 5.2 Permissions matrix

Reusing the plan-tier + role structure already in the codebase, not inventing a new stored-permission table (§2's "server-derived capability flags" precedent):

| Permission | Free plan | Lite plan (`advancedExportEnabled`, no `teamGovernanceAccess`) | Full plan — member | Full plan — admin/owner |
|---|---|---|---|---|
| `export_final_report` | ❌ (no export at all) | ✅ | ✅ | ✅ |
| `export_sources` | ❌ | ✅ | ✅ | ✅ |
| `export_raw_model_outputs` | ❌ | ✅ (solo — own run only) | ❌ | ✅ |
| `export_governance_evidence` | ❌ | N/A — no team governance exists on Lite | ❌ | ✅ |
| `export_reviewer_identity` | ❌ | N/A | ❌ | ✅ |
| `export_sensitive_fields` | ❌ | ❌ | ❌ | ✅, and only per-export justification (§8) |
| `export_organization_reports` (bulk/cross-run) | ❌ | ❌ | ❌ | ✅ |

Computed server-side as a single `exportCapabilities` object per request, mirroring `canManagePanel`/`canVote`/etc. — never trust a client-supplied permission flag.

### 5.3 Data classification model

**Resolved 2026-08-05, see §12.4.** The brief's text was truncated mid-list ("Confidcontrol:"). Rather than leave the reconstructed 4-tier model as an invented, unconfirmed guess, it's now anchored to a real, already-computed signal: `QueryClassification.riskLevel` (`"casual" | "professional" | "high_stakes" | "safety_critical"`), set by the classifier for every run today (`lib/adaptiveSchema/classifier.ts`) and already used to drive `humanReviewNeeded` elsewhere in the governance pipeline. No new taxonomy is introduced — the classification tier is a direct, fixed mapping from `riskLevel`, matching this codebase's own "reuse an existing computed signal, don't invent a parallel one" convention (the same discipline `canManagePanel`-style capability flags follow):

| `riskLevel` (existing, computed per run) | Classification tier (new) | Formats allowed | Reviewer identity | Raw output | Watermark | Retention |
|---|---|---|---|---|---|---|
| `casual` | **Public**-eligible (still requires explicit user action to mark Public — never defaults there) | PDF only | Never | Never | Required | Same as plan default |
| `professional` | **Internal** (default) | PDF, DOCX, JSON, CSV (tabular sections only) | Masked | Never (default) | Optional | Same as plan default |
| `high_stakes` | **Confidential** (recommended default; admin may only raise, never lower) | PDF, DOCX, JSON | Full (if `export_reviewer_identity` granted) | If `export_raw_model_outputs` granted | Required | Shorter than plan default, admin-configurable |
| `safety_critical` | **Restricted** (recommended default; admin may only raise, never lower) | JSON (manifest) + PDF (evidence bundle) | Full | Never (evidence is about the *process*, not raw content) | Required | Legal-hold rules, not plan-tier rules |

An admin may raise a run's classification tier above its `riskLevel`-derived default (e.g. mark a `professional` run Confidential because it discusses an unannounced product), but never lower it below the default — the computed signal is a floor, not a ceiling, matching Constraint #3's least-privilege default.

### 5.4 Sensitive-export warnings (UX)

A blocking confirmation (not a dismissible toast) whenever the resolved classification is Confidential or Restricted, or when `export_raw_model_outputs`/`export_reviewer_identity`/`export_sensitive_fields` are actually exercised (not just granted) — showing exactly which sections will be included, matching the existing project convention of never silently expanding scope (see the multi-reviewer vote-comment privacy precedent: "nobody else, including the team owner, sees another reviewer's comment").

### 5.5 Audit-event contract

New `admin_audit_logs` actions, reusing the existing idempotent `.doc(id).create()` pattern (never the legacy `writeAuditEvent()`'s `.add()`):

- `adaptive_export_generated` — `{exportId, runId, requestingUid, classification, formatRequested, sectionsIncluded: {rawOutputs: bool, reviewerIdentity: bool, ...} — booleans only, never content, governanceDecisionId, reportVersion}`
- `adaptive_export_downloaded`
- `adaptive_export_revoked`

Deterministic ID: `` `adaptive-export:${exportId}:${action}` `` — same collision-avoidance reasoning as `adaptive-review:${decisionId}`.

## 6. Phase 3 — Export data contract (`AdaptiveResearchExportV1`)

Design-level sketch only — not implemented, and deliberately independent of `MemoInput` per §2's verdict.

```ts
interface AdaptiveResearchExportV1 {
  version: 1;
  exportId: string;                  // new, generated at export time — never reused
  runId: string;

  schemaId: QueryType;
  schemaVersion: 1;                  // = PersistedAdaptiveOutputV1.version at capture time
  reportVersion: number;             // NEW concept (§1) — monotonic per (runId), incremented
                                      // each time an export is generated for this run, so
                                      // "Superseded" is a simple version-number comparison,
                                      // not a new mutable-record versioning system.
  governanceRecordVersion: 1;        // = GovernanceRecordV1.version at capture time

  generatedAt: string;               // ISO — this export's own generation time
  requestedBy: string;               // uid, never displayed in the export body itself

  classification: "public" | "internal" | "confidential" | "restricted";
  reportStatus:                      // the §4.1 status, frozen at generation time
    | "unreviewed_in_queue" | "not_reviewed_no_review_configured"
    | "approved" | "approved_with_conditions"
    | "changes_requested" | "rejected" | "owner_override"
    | "incomplete" | "superseded";

  snapshot: {
    decisionReceipt: AdaptiveDecisionReceipt;      // frozen copy, not a live reference
    schemaResult: /* redacted per exportCapabilities at generation time */ unknown;
    approvedSources: string[];
    governanceSummary: {
      status: GovernanceRecordV1["humanReview"]["status"];
      conditions?: string[];
      decidedVia?: GovernanceRecordV1["humanReview"]["decidedVia"];
      reviewedAt?: string;
      // reviewerId/reviewerName ONLY if export_reviewer_identity was granted
      // AND exercised — otherwise entirely absent, not masked-in-place.
    };
  };

  // Present only when export_raw_model_outputs was exercised.
  rawModelResponses?: AdaptiveModelResult[];

  manifest: ExportManifest;          // §6.1
}

interface ExportManifest {
  exportId: string;
  runId: string;
  schemaVersion: 1;
  exportedSections: string[];        // e.g. ["decisionReceipt", "approvedSources"] — never content
  fileHash: string;                  // sha256 of the generated artifact bytes
  createdAt: string;
  requestingUser: string;            // uid
  governanceDecisionId?: string;     // links to the humanReviewHistory decisionId, if any
  finalReportVersion: number;        // = reportVersion above
}
```

**Why this satisfies Constraint #1 without new source-of-truth infrastructure:** `snapshot` is a deep, frozen copy taken once at generation time — never a live reference into `runs/{runId}`. The immutability guarantee lives entirely in the export artifact's own storage (write-once object storage, §9), not in a change to how `adaptiveOutput`/`governanceRecord` are stored today. This is the cheapest correct design and matches the project's existing bias toward additive changes over rewrites (every Milestone 2/governance step to date has been additive).

## 7. Phases 4–7 — condensed rollout (design intent only, not scheduled here)

| Phase | Scope | Explicitly excluded from that phase |
|---|---|---|
| 4. PDF pilot | Final reviewed report, category-specific structure (reuses each schema's existing renderer structure — `ComparisonMatrixView`'s grid, `RiskAnalysisView`'s register — as the PDF's section layout, not a new generic template), citations, consensus/disagreement, uncertainty, governance summary, status watermark (§4), page numbers, manifest, accessibility tags | Raw model output (default), DOCX/JSON/CSV |
| 5. DOCX | Editable version of the same content, headings/tables/citations/status preserved | Must visually/structurally flag "edited copies are no longer canonical" — the manifest's `fileHash` becomes meaningless the moment a user edits the file locally; the DOCX itself should carry a footer notice, since there's no way to prevent local edits |

**Recommendation, matching the brief's own conclusion:** PDF is the correct first implementation target, not all four formats — it's the only format where "decision-ready, audit-ready" and "status is unmistakable" (watermark) are naturally enforced by the format itself (a PDF viewer can't hide the watermark the way a JSON consumer could ignore a status field).

## 8. Export as a security boundary (Constraint #7)

| Threat | Design-level mitigation |
|---|---|
| CSV formula injection | Prefix any cell value starting with `=`, `+`, `-`, `@`, tab, or CR with a leading `'` before serialization — apply to every CSV cell, not just user-authored fields (a model can produce a string starting with `=` too) |
| Malicious links | Strip/neutralize `javascript:`/`data:` URI schemes from any exported hyperlink; source URLs pass through a scheme allowlist (`https:`, `http:`) before being rendered as clickable |
| Unsafe HTML | Never render raw model text as HTML in any export format — plain text or escaped markdown only, even in PDF/DOCX generation |
| Prompt/model output containing executable markup | Same as above — model output is untrusted input to every export renderer, treated identically to user-submitted content |
| DOCX relationship attacks | Generate via a vetted library with a fixed, allowlisted relationship set; never accept a user-supplied DOCX template to fill in |
| Oversized content | Hard size caps per section (reuse the same `maxItems`/`maxWords` discipline `schemaRegistry.ts` already enforces on model output — the export renderer inherits those caps, doesn't need its own) |
| Source-excerpt copyright/confidentiality leakage | Sources are already stored as plain labels (`sources: string[]`), never full excerpts — no new leakage surface introduced by exporting them |
| Path traversal | `exportId` is a generated UUID, never derived from user input, and never used to construct a filesystem path directly — object-storage keys are namespaced server-side |
| Insecure temporary files | Generate in-memory or in a request-scoped temp directory that's guaranteed cleaned up (matches the project's existing "never leave scratch state" discipline); never write to a predictable shared path |
| Unauthorized object-storage access | Bucket/object ACLs default-deny; every read goes through a signed URL minted per-request, never a public bucket policy |
| Predictable download URLs | Signed, time-limited, single-use URLs (§9) — `exportId` alone must never be sufficient to fetch the file |

## 9. Post-export controls (Constraint #8)

Recommendations, flagged as decisions to confirm rather than settled defaults:

- **Download links expire** — 24h for Internal, 1h for Confidential/Restricted. **Resolved 2026-08-05, see §12.5:** confirmed via codebase search that no signed-URL/object-storage infrastructure exists anywhere today (no prior art to align with — this is genuinely greenfield, matching §1's finding that no export/storage system exists at all). These numbers stand as the initial defaults, admin-configurable per §5.3's classification table, not derived from an existing policy.
- **Exports may be regenerated**, always producing a new `exportId`/`reportVersion` — never overwrite an existing export artifact in place (that would itself violate Constraint #1).
- **Exports may be revoked** by an admin — revocation invalidates the signed URL and logs `adaptive_export_revoked`; the artifact's manifest is retained for audit even after revocation (the file, not the metadata, becomes inaccessible).
- **Users can see their own export history** — a list view driven by `admin_audit_logs`' `adaptive_export_*` actions, scoped to their own `requestingUser`.
- **Admins can investigate unusual export activity** — reuse the existing `GET /api/governance/audit` reader with the new actions added to its allowlist (§5.5), no new investigation surface needed.
- **High-risk exports require additional confirmation** — any export where `classification` resolves to Confidential/Restricted, per §5.4.

## 11. Risks

1. **Reconciling plan-tier gating with team-role gating with the new per-field permissions is three independent axes** (§5.2's table already shows this getting complex at just 4 plan/role combinations × 7 permissions) — recommend a single `resolveExportCapabilities(uid, runId)` function as the one place this logic lives, mirroring `routeClassifiedQuery()`'s "exactly one place this logic lives" precedent.
2. **`reportVersion`/"Superseded" is a new concept with no existing field to build on** — it's cheap to add (a counter), but it's still new persisted state, meaning Phase 3 is not purely additive-on-export; a small schema addition to the run document (or a new small collection) is needed. Flagged so it isn't discovered mid-implementation.
3. **DOCX "edited copies are no longer canonical" cannot be technically enforced** — only a footer notice; this is a real limitation, not a solvable one, worth surfacing to stakeholders before DOCX is scoped.
4. **`export_organization_reports` (bulk/cross-run export) is the least-specified permission in the brief** — no field-level matrix exists for it because it's a different shape entirely (many runs, not one). Recommend scoping it out of Phases 3–4 entirely and treating it as its own design pass once single-run export is stable.

## 12. Open questions — resolved 2026-08-05

All 5 are resolved below. Each resolution is either a **fact**, confirmed by reading the actual code (not re-running or changing anything in production), or a **design decision**, made explicitly in the absence of a separate product stakeholder in this conversation — flagged as such rather than presented as settled fact, so it can still be overridden on review.

1. **§Precondition — fact.** No structured canary was run for `ADAPTIVE_SCHEMAS_ENABLED`/`ADAPTIVE_VERIFICATION_ENABLED`. Both flags were set directly to 100% production traffic (not a limited-team rollout matching this project's own `docs/operations/multi-reviewer-governance-runbook.md` §11 convention), verified only by two manual live spot-checks. Resolution: treat the next real business week of production traffic as the monitoring window going forward (existing `admin_audit_logs`/telemetry, no new tooling); Phase 1 implementation is not blocked on it. See the updated Precondition line above.

2. **§4.1 — fact, confirmed by code read.** `app/api/run-panel/route.ts`'s governance-initialization block gates `initializeAdaptiveGovernanceRecord()` on `adaptivePayload.persistenceStatus === "saved"` only — no team, plan, or `teamGovernanceAccess` check. Every adaptive run on every plan gets a `GovernanceRecordV1` with `humanReview.status: "unreviewed"`, whether or not it was ever routed to a reviewer. Resolution: "Unreviewed" is split into two status labels (§4.1's table), disambiguated by `adaptiveTeamReviewProjectionStatus` / `routeAdaptiveTeamReview()`'s reason — this is a genuine, reusable existing signal, not a new field.

3. **§4.1 — design decision.** `changes_requested` is kept as its own 8th status, distinct from "Rejected." Rationale unchanged from the original recommendation: rejection is terminal, `changes_requested` implies a resubmission path exists, and collapsing the two would misrepresent an in-progress state as final — inconsistent with Constraint #2's "unmistakable" requirement, which cuts both ways (a status must be exactly as final as it actually is).

4. **§5.3 — design decision, but now grounded rather than invented.** Instead of confirming the brief's cut-off classification list as literally written (impossible — the text is genuinely truncated), the reconstructed 4-tier model is now anchored to `QueryClassification.riskLevel`, an already-computed, already-used signal (`casual`/`professional`/`high_stakes`/`safety_critical`) rather than a new taxonomy invented from scratch. This is a stronger resolution than either guessing at the brief's missing word or leaving the tier boundaries undefined — see the updated §5.3 table.

5. **§9 — fact, confirmed by code search.** No signed-URL, object-storage, or export-file infrastructure exists anywhere in the codebase today (`grep` for `getSignedUrl`/`signedUrl`/`Storage()` returns nothing) — there is no existing retention precedent to align with or contradict. The 24h/1h defaults stand as the initial recommendation, admin-configurable, not derived from prior art because none exists.
